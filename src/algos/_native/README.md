# algos._native — ускоренные реализации (шаг 3)

Каждый модуль может **не импортироваться**, и это нормально: соответствующий backend просто будет недоступен.

| Модуль | Backend | Чем ускоряет | Нужно |
|--------|---------|--------------|-------|
| `vectorized.py` | `numpy` | целые операции над массивами вместо цикла на Python | numpy |
| `numba_impl.py` | `numba` | JIT в машинный код; `prange` — потоки без GIL | numba (`--extra fast`) |
| `c_impl.py` | `c` | ctypes-обёртка над `libalgos.so` из [`native/`](../../../native/README.md) | `make -C native` |
| `cuda_impl.py` | `cuda` | те же векторные алгоритмы на GPU через CuPy | CuPy + NVIDIA GPU (`--extra gpu`) |
| `limbs.py` | — | общие хелперы длинной арифметики (uint64-массивы) | numpy |
| `ids.py` | — | `compact_ids`: значения → плотные id `[0, m)` (словарное кодирование), чтобы индексировать массивы, а не хэшировать | numpy (+numba для O(n)) |

## Что внутри

| Алгоритм | numpy / cuda | numba | C |
|----------|--------------|-------|---|
| Two Sum | sort + `searchsorted` (без хэша, зато всё векторно) | своя хэш-таблица, открытая адресация | то же на C |
| Two Sum batch | упаковка `(задача << 40) \| значение` в один ключ → один глобальный sort | `prange` по задачам | — |
| сложение | **carry-lookahead**: generate/propagate/kill + `cumsum` | **carry-select**: куски параллельно, скан, +1 | **ADC**: `_addcarry_u64` |
| сумма N чисел | **carry-save**: суммы столбцов 32-битных половин | то же, `prange` по строкам | — |
| окно без повторов | `left = cummax(prev_k + 1)`; на GPU cummax удвоением шага (Hillis–Steele) | LastIndex на массиве; batch: `prange`, буфер на поток с точечным обнулением | то же на C |
| k-й из двух (разрез) | — | разрез; «справа пусто» — флаг (numba нужен один тип результата) | то же на C |
| k-й из K (по значению) | — | `searchsorted` по `typed.List` | `upper_bound` без ветвлений, массив указателей |
| сжатие id | `np.unique` (сортировка) | **хэш-таблица** (как в Two Sum), O(n) | — |

## Правила

1. **Тот же контракт, что у python-эталона.** Не «примерно так же», а ровно: тесты в `tests/algos/` прогоняют все backend'ы одними и теми же проверками.
2. **Регистрация** — в модуле функции (`algos/<техника>/*.py`) через `register_optional(backend, module, attr, min_n=...)`.
3. **`min_n` и `priority` — только по замеру** (`benchmarks/`).
4. Если backend не поддерживает часть входов (например, `base > 2^64`), публичная функция сама переключается на `python`, а не backend бросает исключение.

## Уроки, оплаченные замерами

- **Накладные расходы вокруг горячего цикла важнее самого цикла.** Валидация (`min`/`max`) и `flatnonzero` стоили больше, чем сложение: C ускорился в 6 раз, когда их убрали.
- **`ctypes ... data_as()` стоит ~5 µs на вызов.** Используем `c_void_p` + `arr.ctypes.data`.
- **numba `parallel=True` поднимает пул потоков на каждом вызове (~1 ms).** Для небольших входов нужна отдельная функция без `parallel`.
- **Смешивание `uint64` и `int64` в numba даёт `float64`**, а float нельзя использовать как индекс массива. Приводим явно: `np.int64(...)`.
- **GPU платит ~5 ms за запуск и копирование по PCIe.** Он выгоден, только когда на элемент приходится много работы или данные уже лежат на GPU.
- **Python-цикл по задачам держит GIL**, даже если каждая задача решается в C. Для множества мелких задач нужен один вызов на весь пакет (`prange`), а не потоки.
- Первый вызов numba-функции — это JIT-компиляция (~1 s). `cache=True` сохраняет результат на диск.
- **Закон Амдала.** Алгоритм ускорили в 4 раза, а детектор целиком — на 15%: 75% времени уходило на группировку и сортировку Python-объектов. Перед ускорением меряем, **что** занимает время.
- **Сортировка строк дорогая.** `np.unique` по миллиону строк сделал пакетный путь медленнее Python. Значения стоит кодировать в номера как можно раньше (словарное кодирование).
- **Для O(log) вызов дороже работы.** Ядро разреза в numba — 0.8 µs, а через публичную функцию — 4.5 µs: проверка входа, диспетчер, распаковка результата. Ускорять такое имеет смысл, только если вход уже numpy, а выигрыш ×2–3, а не ×50.
- **ctypes дороже numba на крошечных вызовах.** `a.ctypes.data` стоит ~1.6 µs **на массив**, `c_int64()` + `byref` ещё ~0.5 µs. Разрез на C (11 µs) проиграл numba (4.5 µs), хотя ядро на C не медленнее.
- **`numba.typed.List` стоит ~2 µs на массив.** Для «списка массивов» C с массивом указателей быстрее numba в 1.4–3.5 раза, хотя ядра почти одинаковые.
- **Отсутствующая переменная окружения — 1.2 µs.** `os.environ.get` внутри ловит `KeyError` (есть ключ — 0.45 µs). `auto` в `Dispatcher` платит это на каждом вызове; на горячем пути O(log) лучше передавать `backend` явно.
- **Бинпоиск без ветвлений быстрее и на больших массивах.** Гипотеза «ветвления помогают предзагрузке памяти» не подтвердилась: branchless быстрее до ×2.7 (K = 1000), а `__builtin_prefetch` там даже вредит.
- **Сужение окна поиска не помогло.** Верхние уровни бинпоиска для соседних `mid` и так в кэше, а промахи на нижних уровнях сужение не убирает.
- **Узкий диапазон значений делает бинпоиск по значению почти бесплатным.** Цены ±20 копеек → ~6 итераций вместо 31, и Python на списках сравнялся с C на numpy. В бизнес-слое нативный код не понадобился, а 25% дало «не считать медиану второй раз, если выбросов нет».
- **Векторизация не спасает плохую асимптотику.** Scan за O(n log n) с 10 проходами по памяти проиграл простому циклу на Python за O(n).
