# fintech/scenarios — антифрод по сценариям событий сессии

**Боль.** Самые дорогие мошенничества в онлайн-банке — не одно странное событие, а **цепочка** нормальных по отдельности. Классика — захват аккаунта (account takeover, ATO): вход с нового устройства → смена телефона (чтобы SMS шли мошеннику) → вывод денег. Каждый шаг легален: люди меняют телефоны и выводят деньги. Подозрительна последовательность. Аналитики антифрода описывают такие сценарии правилами и меняют их каждую неделю, потому что мошенники меняют схемы.

**Алгоритм.** [LeetCode 10. Regular Expression Matching](../../../../problems/0010_regular_expression_matching/README.md): «строка» — типы событий сессии по времени, «шаблон» — правило аналитика с `.` (любое событие) и `*` (ноль или больше). Вызов: `algos.automata.SimplePattern.from_tokens(...)`, пошагово `start` / `step` / `accepts`.

## Почему не `re`

Правила пишут люди, и рано или поздно кто-то напишет `login* login* login* … payout`. На сессии из 24 входов без вывода `re.fullmatch` тратит на такое правило **30 секунд** (backtracking, экспонента: README задачи 10). Одно неаккуратное правило остановило бы обработку платежей для всех клиентов: это ReDoS, только своими руками. Здесь правило компилируется в НКА, и время линейно на любом правиле: те же 24 входа — **~40 µs** (`demo.py`).

## Правило (`ScenarioRule`)

| Поле | Смысл |
|------|-------|
| `name` | имя для отчёта |
| `pattern` | токены через пробел: `имя_события`, `.` — любое одно, `имя*` / `.*` — ноль или больше |
| `action` | `review` (аналитику) < `step_up` (2FA / звонок) < `block` (остановить операцию) |
| `mode` | `contains` — сценарий где-то в сессии, тревога **сразу на последнем событии сценария**; `session` — шаблон описывает всю сессию, решается при её закрытии |

Правила из `demo.py`:

| Правило | Шаблон | Режим → действие |
|---------|--------|------------------|
| `ato_classic` | `login_new_device .* change_phone .* payout` | contains → block |
| `new_payee_payout` | `add_payee payout` (вывод сразу после добавления получателя) | contains → step_up |
| `brute_force_success` | `login_failed login_failed login_failed login_failed* login_success` | contains → step_up |
| `bot_session` | `login payout logout*` (вся сессия — вход и вывод, ничего не просмотрено) | session → review |

## Бизнес-детали

- **Тревога до того, как деньги ушли.** В онлайн-режиме (`StreamingScenarioEngine.observe`) правило `contains` срабатывает на самом событии `payout`. Операцию ещё можно остановить, а не расследовать потом. Это прямо следует из НКА: он читает поток по событию и не ждёт конца сессии.
- **Память не зависит от длины сессии.** На открытую сессию хранится одно число на правило (битовая маска состояний), сами события — нет. Сессии без событий дольше 30 минут закрываются `close_idle` (как таймаут на сайте), их память освобождается.
- **Пакетный режим = онлайн по отсортированной истории.** Результаты совпадают по построению, а логика срабатывания живёт в одном месте. Онлайн-режим требует порядка по времени внутри сессии и падает на нарушении: тихо «обработать как пришло» значило бы пропустить сценарий.
- **Проверка правил при загрузке** (`RuleError`, `lint_rules`, ручка `rules/check`):
  - синтаксис (`**`, заглавные, дефисы) — ошибка;
  - правило-«всегда» (`login* .*` совпадает с пустой сессией, значит с любой) в режиме `contains` — ошибка: оно бы заблокировало всех;
  - событие вне каталога (`chnage_phone`) — предупреждение: опечатка делает правило мёртвым, и никто этого не заметит;
  - повтор имён — предупреждение.
- **Одна сессия — один вердикт.** Правило срабатывает в сессии один раз; итог по сессии — самое строгое действие (`decide`).
- **Деньги — копейки (int).** В тревоге — сумма денежных событий сессии до срабатывания: аналитик сразу видит, сколько стоит кейс.

## Ограничения (куда развивать)

- **Нет окна по времени** («смена телефона и вывод в течение часа»). НКА на битовой маске помнит, *где* мы в шаблоне, но не *когда* начали. Нужен Pike VM: для каждого состояния хранить время начала самого свежего пути. Пока временем ограничивает сама сессия (таймаут 30 минут).
- **Нет атрибутов событий** (`payout` больше 100 000 ₽, новый получатель из другой страны). Решается расширением алфавита: событие классифицируется в тип до НКА (`payout_large`).
- **Сценарии внутри сессии.** ATO, растянутый на несколько сессий (сменил телефон сегодня, вывел завтра), так не ловится; нужна «сессия» по пользователю за сутки.
