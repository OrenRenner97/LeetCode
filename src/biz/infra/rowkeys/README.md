# infra/rowkeys — развёрнутые ключи строк против hotspot'а

## Боль

В HBase, Bigtable, Cassandra с упорядоченным разбиением и любой таблице, которая режется на регионы по **диапазонам ключа**, последовательные id — классическая ловушка. Если ключ — номер заказа, автоинкремент или время, все новые записи попадают в конец пространства ключей, то есть в **один регион на одном сервере** (hotspot). Остальные простаивают, пропускная способность записи равна пропускной способности одного узла, а авто-сплит лишь переносит «горячий хвост» на новый регион.

Один из стандартных приёмов (HBase Reference Guide, раздел «Reversing the key») — **развернуть ключ**: записать цифры id задом наперёд. Быстрее всего меняется младшая цифра, теперь она первая, и соседние id разлетаются по всему пространству ключей.

## Связь с задачей

Разворот — это **LeetCode 7. Reverse Integer** (`algos.reverse_digits`). Оба подводных камня задачи здесь становятся продакшн-инцидентами:

- **Ведущие нули и обратимость.** LeetCode теряет их (120 → 21), и разворот не обратим: заказы 12, 120 и 1200 получили бы один ключ 21 и перезаписали бы друг друга. Поэтому ключ строится в **фиксированной ширине** `width`: «0120» → «0210». Это взаимно однозначно, и `decode` восстанавливает id.
- **Переполнение колонки.** Ключ хранится в int32/int64. Хочется взять `width = 19`, «ведь все id влезают в int64». Но первая цифра ключа — последняя цифра id, и id на …99 даёт ключ 9.9·10¹⁸ > 2⁶³ − 1. На 100 000 реальных id подряд не влезают **7.8%**, то есть каждый ~13-й заказ падает при вставке. Это ровно `return 0` из LeetCode, только в проде. `max_safe_width`: int32 → 9, int64 → 18, uint64 → 19.

## Что есть

- `KeyScheme(storage, width, reverse)` — тип колонки (`int32`, `int64`, `uint64`, `string`), ширина (по умолчанию безопасная), прямой или развёрнутый ключ. `safe` — влезает ли любой id.
- `encode(id, scheme)` / `decode(key, scheme)` — взаимно обратны. `KeyOverflow`, если ключ не влезает в колонку (бывает только при `safe = False`).
- `audit(ids, scheme)` — какие из реальных id не получат ключ. Нужно перед миграцией схемы.
- `region_loads(ids, scheme, regions)` и `compare_sequential(start, count, scheme, regions)` — раскладка пачки по регионам заранее разбитой таблицы: `loads`, `hottest_share`, `skew` (максимум / среднее), `regions_touched`.

## Результат (`python -m biz.infra.rowkeys.demo`)

100 000 заказов подряд, int64, `width = 18`, 16 регионов:

| Ключ | Самый горячий регион | skew | Регионов |
|------|----------------------|------|----------|
| прямой (id) | 100% | 16.0 | 1 |
| развёрнутый | 6.25% | 1.00 | 16 |

## Цена приёма (честно)

- **Пропадают диапазонные запросы по id.** «Заказы с 1 000 000 000 по 1 000 099 999» по прямому ключу — один скан одного региона, по развёрнутому — обход всех регионов (`regions_touched` показывает это же число). Приём подходит, когда читают по точному id (get по ключу), а не диапазонами.
- **Ровно только для последовательных id.** Распределение задаёт младшая цифра. Если id идут шагом 10 (шардированный автоинкремент), первая цифра ключа у всех одинакова — нужно смотреть `region_loads` на своих данных.
- **Альтернативы:** соль (префикс `hash(id) % B`) — ровно при любом шаге, но для get нужно знать соль, а скан — B запросов; хэш-ключ — ровно, но не обратим без хранения id. Разворот обратим, детерминирован и бесплатен.
