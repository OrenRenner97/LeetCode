# benchmarks/

Замеры, из которых берутся пороги `min_n` и порядок `priority` в `algos`. Результаты с выводами записываются в README задачи (раздел «Шаг 3»).

```bash
uv run benchmarks/<файл>.py
```

| Файл | Задача | Что меряет |
|------|--------|------------|
| `two_sum.py` | 1 | учебные альтернативы против библиотеки (шаг 1) |
| `two_sum_backends.py` | 1 | один запрос: python / numpy / numba / c / cuda, вход list и ndarray |
| `two_sum_parallel.py` | 1 | много клиентов: потоки, процессы, numba `prange`, GPU |
| `add_two_numbers.py` | 2 | учебные альтернативы на связных списках (шаг 1) |
| `add_two_numbers_backends.py` | 2 | одно огромное число + аудит N балансов uint256 |
| `longest_substring.py` | 3 | учебные альтернативы на трёх видах входа (маленький / средний / максимальный ответ) |
| `longest_substring_backends.py` | 3 | одна последовательность, batch по источникам, детектор целиком по этапам, потоковый режим |

## `bench.py`

```python
bench(impls={"имя": fn, ...}, make_input=lambda n: (args...), sizes=[10**3, 10**6], repeat=5, warmup=1, check=True)
```

- Печатает медиану по `repeat` прогонам и во сколько раз реализация медленнее лучшей.
- `warmup` — прогоны без замера: JIT numba, прогрев GPU, кэши.
- `check=True` сверяет ответы реализаций. Для сложных результатов ставим `check=False` и сверяем вручную до замера.

## Как не обмануть себя

- **Ноутбук: частота плавает, разброс ±30%.** Сравнивать стоит порядки и тенденции, а не проценты. Важные цифры перемеряем.
- **Худший случай задаём явно** (пара в конце, цепочка переноса), иначе ранний выход покажет фантастику.
- **Данные перемешанные.** Отсортированный вход однажды подыграл Timsort и исказил вывод.
- **Конвертация входа тоже время.** Меряем и list, и ndarray: в реальности данные приходят из бизнес-слоя.
- **Сначала проверяем генератор.** Дважды ошибка была в генераторе, а не в коде.
