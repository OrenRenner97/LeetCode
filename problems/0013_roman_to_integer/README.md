# 13. Roman to Integer

[LeetCode](https://leetcode.com/problems/roman-to-integer/) · Easy · Hash Table, Math, String

## Условие (кратко)
Корректная римская запись s (1 ≤ len ≤ 15, число из [1, 3999]) → число. Меньший символ перед большим вычитается; таких пар шесть: IV, IX, XL, XC, CD, CM.

## Решение (solution.py): таблица из 13 токенов, сначала пара, потом один символ

**Идея:** те же 13 номиналов, что в задаче 12 (7 символов + 6 вычитательных пар). Идём по строке: если два символа подряд — вычитательная пара, прибавляем её и шагаем на 2, иначе прибавляем один символ.

**Время:** O(k), k = len(s) ≤ 15 · **Память:** O(1)

Корректно: на всех 3999 числах (запись из независимого эталона `to_roman` в тестах) возвращает исходное число.

Что можно улучшить:
- **Срез `s[i:i+2]` делается дважды за шаг.** Каждый — новая строка и её хэш: один раз в `in`, второй — при индексации. `d.get(s[i:i+2])` один раз и проверка на `None` — вдвое меньше работы. Но и так это главный тормоз: на MMMDCCCLXXXVIII (15 символов, пар нет) Solution в 4 раза медленнее простого прохода по символам.
- **Проверка `i + 1 < len(s)` лишняя** (но безвредная): на последнем символе `s[i:i+2]` — это один символ, он тоже есть в таблице, `i += 2` выведет из цикла. Явная проверка понятнее, так что можно оставить.
- **`__ROMAN_TO_INT`** с двумя подчёркиваниями включает name mangling (`_Solution__ROMAN_TO_INT`). Для «приватной» константы класса принято одно подчёркивание; два нужны только против конфликта имён в наследниках.
- **Невалидный вход молча принимается**: `IIII` → 4, `IM` → 1001, `VV` → 10. LeetCode обещает корректную запись, а библиотеке так нельзя (см. шаг 1.5).
- `while i < len(s)` с ручным индексом в CPython дороже `for c in s`: каждый шаг — `len`, сравнение, индексация, сложение.

## Шаг 1. Альтернативы (alternatives.py)

Пакет из 10⁵ строк через `list(map(f, strs))`, Python 3.12, медиана из 5. Ноутбук шумит ±30% — сравнивать порядки.

| Подход | Время | Память | all | long (3888) | short (M) | subtr (4/9 везде) | Идея |
|--------|-------|--------|-----|------|-------|-------|------|
| Solution | O(k) | O(1) | 266 ms (2.7 µs) | 541 ms | 27 ms | 244 ms | пара или один символ, срезы `s[i:i+2]` |
| SubtractNext | O(k) | O(1) | 87 ms | 126 ms | **24 ms** | 95 ms | меньше следующего — вычитается |
| ReverseScan | O(k) | O(1) | 90 ms | 133 ms | 32 ms | **83 ms** | справа налево, меньше правого — вычитается |
| PairCount | O(k) | O(1) | 140 ms | **117 ms** | 65 ms | 175 ms | `sum(map(...))` + поправка через `str.count` |
| ReplacePairs | O(k) | O(k) | 143 ms | 126 ms | 73 ms | 157 ms | 6 × `replace` раскрывают пары, потом сумма |
| DigitRegex | O(k) | O(1) | 159 ms | 153 ms | 88 ms | 122 ms | регулярка по разрядам, группы → таблицы; заодно проверяет каноничность |
| **FullLookup** | O(k) | O(4000) | **12 ms (0.12 µs)** | **9.5 ms** | **8.2 ms** | **12 ms** | словарь всех 3999 записей |

Входы: all — случайные 1..3999; long — MMMDCCCLXXXVIII; short — M; subtr — тысячи + 4/9 в каждом из трёх младших разрядов (MMCDXCIV и т.п.).

- **Простой проход по символам (SubtractNext, ReverseScan) — ×3 к Solution.** Одна операция на символ: словарь + сравнение. Нет срезов и не создаются строки. Какой из двух быстрее — в пределах шума.
- **«Всё на C» (PairCount, ReplacePairs) выигрывает только на длинных строках.** На long (15 символов, пар нет) PairCount — лучший из «честных»: `sum(map(...))` без Python-цикла, а шесть `in s` возвращают False сразу. На коротких фиксированная цена (6–12 вызовов методов строки) больше самого цикла: на M — ×2.7 к SubtractNext.
- **DigitRegex медленнее, зато бесплатно проверяет корректность**: неканоническое (`IIII`, `IC`, `MMMM`) просто не совпадёт. Это прямое обращение DigitTables из задачи 12.
- **FullLookup — ×7–13 к лучшему циклу.** Корректных записей всего 3999, словарь ~400 КБ строится один раз. И сразу валидирует: всё, чего нет в словаре, — неканоническая запись. Оговорка: бенчмарк гоняет одни и те же объекты строк, а CPython кэширует хэш строки в объекте — после первого прогона хэш не считается. Для свежей строки из 15 символов это добавляет ~20–30 ns, порядок не меняется.

## Шаг 1.5. Библиотека → `algos.from_roman`
`src/algos/arithmetic/roman.py`, рядом с `to_roman` из задачи 12. Отличия от LeetCode-версии:
- **Строгий разбор: только каноническая запись, иначе `None`.** Каноническая — ровно то, что выдаёт `to_roman`: `IIII`, `VV`, `IC`, `IM`, `MMMM`, `""` → `None`. Решение LeetCode молча вернуло бы 4, 10, 99, 1001, 4000.
- **Регистр:** весь верхний или весь нижний (`xiv` → 14), смешанный (`XiV`) → `None`. Пробелы по краям не срезаются — это забота вызывающего.
- **Не str** (`bytes`, `None`, число) → `TypeError`.
- Реализация — FullLookup: словарь всех 3999 записей в двух регистрах (~8000 ключей) строится при импорте из таблицы `to_roman`. Валидация бесплатна: чего нет в словаре — то не каноническая запись. Импорт модуля целиком ~5 ms.

Цена API, один вызов на строке `MCMXCIV`, собранной в рантайме, лучшее из 5:

| | время |
|-|-|
| Solution | 2.3 µs |
| SubtractNext | 1.0 µs |
| FullLookup (без проверок) | 151 ns |
| `from_roman(s)` | **148 ns** |
| `from_roman("IIII")` → `None` | 146 ns |

- Проверка типа почти ничего не стоит — `from_roman` в пределах шума с голым FullLookup, ×15 к Solution. Отказ так же быстр, как успех.

Тесты (`tests/algos/test_roman.py`): LeetCode-примеры; весь диапазон 1..3999 — `from_roman(to_roman(n)) == n == Solution`, в обоих регистрах и на строках, собранных в рантайме; 27 неканонических записей → `None`; 20 тыс. случайных строк из I V X L C D M против канонической регулярки и независимого подсчёта; `TypeError`.
