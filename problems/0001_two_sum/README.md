# 1. Two Sum

[LeetCode](https://leetcode.com/problems/two-sum/) · Easy · Array, Hash Table

## Условие (кратко)
Найти индексы двух разных элементов `nums`, сумма которых равна `target`. Ответ ровно один.

## Решение (solution.py)
**Идея:** перебор всех упорядоченных пар `(i, j)`, `i != j`.
**Время:** O(n²), ровно n² итераций в худшем случае. **Память:** O(1).

Что можно улучшить, не меняя асимптотику:
- каждая пара проверяется дважды, `(i, j)` и `(j, i)`: если брать `j > i`, итераций станет n²/2, а проверка `i != j` не понадобится;
- `target - nums[i]` можно посчитать один раз на внешнюю итерацию;
- `range` вместо второго `enumerate` экономит создание кортежей во внутреннем цикле.

Вместе это даёт ×4 (см. бенчмарк), но асимптотика остаётся O(n²).

## Шаг 1. Альтернативы (alternatives.py)

| Подход | Время | Память | Когда лучше |
|--------|-------|--------|-------------|
| Solution (твой) | O(n²) | O(1) | никогда, кроме n ≈ 10 |
| BruteHalf | O(n²) | O(1) | крошечные n или очень жёсткий лимит памяти |
| SortTwoPointers | O(n log n) | O(n)* | данные уже отсортированы (тогда O(n) / O(1)) или нужны **все** пары |
| HashTwoPass | O(n) | O(n) | учебный шаг к one-pass |
| **HashOnePass** | **O(n)** | **O(n)** | **по умолчанию** |

\* O(n), потому что надо помнить исходные индексы. Если вход уже отсортирован и вернуть нужно значения или отсортированные индексы (задача [167](https://leetcode.com/problems/two-sum-ii-input-array-is-sorted/)), память O(1).

### Ключевая идея: «что мне нужно» вместо «с кем сложить»
Перебор спрашивает: «с каким `j` сложить `nums[i]`?», и это n вопросов по n вариантов.
Хэш переворачивает вопрос: «мне нужно **конкретное** число `target - x`, встречалось ли оно?». Ответ на такой вопрос стоит O(1) благодаря словарю. Получается n вопросов по O(1) каждый, итого O(n).

### Почему one-pass лучше two-pass
- Один проход вместо двух.
- Ранний выход: если пара в начале массива, остальное даже не читаем. Это видно в бенчмарке, где пара стоит в начале массива.
- Нет отдельной проверки `j != i`: ищем дополнение **до** вставки текущего элемента, поэтому с самим собой он не спарится.
- Дубликаты `[3, 3]` работают естественно: первая 3 лежит в `seen`, когда приходит вторая.
- Подходит для **потока** данных: элементы обрабатываются по мере поступления. Это пригодится в шаге 2.

### Trade-off время ↔ память
- O(1) памяти: только перебор O(n²) или сортировка на месте O(n log n). Но сортировка на месте теряет индексы, так что для этой задачи это возможно, только если нужны значения, а не индексы.
- O(n) времени: только с O(n) памяти под хэш-таблицу.
- Быстрее O(n) нельзя: нужно хотя бы прочитать вход.

### Бенчмарк (худший случай: пара в самом конце, `uv run benchmarks/two_sum.py`)

| n | user_brute | brute_half | sort_two_pointers | hash_two_pass | hash_one_pass |
|---|-----------|------------|-------------------|---------------|---------------|
| 100 | 2.19 ms | 0.59 ms | 55 µs | 62 µs | 55 µs |
| 1 000 | 206 ms | 55 ms | 476 µs | 519 µs | **471 µs** |
| 3 000 | 2.07 s | 538 ms | 1.54 ms | 1.96 ms | **1.31 ms** |
| 10 000 | ~23 s (оценка) | — | 5.6 ms | 6.0 ms | **4.7 ms** |
| 1 000 000 | ~64 ч (оценка) | — | 482 ms | 754 ms | 553 ms |

- На 3000 элементах хэш быстрее твоего решения примерно в 1600 раз, и разрыв растёт квадратично.
- На 10⁶ `sort_two_pointers` обогнал хэш, но только потому, что тестовый массив почти отсортирован: Timsort на таком входе работает за ~O(n). На случайных данных сортировка проиграет. Это хорошая иллюстрация того, что асимптотика ≠ скорость на конкретных данных.
- Если пара стоит в начале массива, `hash_one_pass` и перебор выходят за микросекунды, а `two_pass` и `sort` всегда платят за полный проход.

## Шаг 1.5. Библиотека → `algos.find_pair_with_sum`

`src/algos/hashing/pair_sum.py`. Отличия от LeetCode-версии:
- нет пары → `None` (на LeetCode ответ гарантирован);
- чёткий контракт: возвращается пара с минимальным `j`, среди них с минимальным `i`, поэтому результат детерминирован и «самые ранние элементы первыми»;
- `seen.setdefault`, чтобы при дубликатах помнить первое вхождение;
- `backend=` / `ALGOS_BACKEND`: выбор реализации (пока только `python`).

## Шаг 2. Бизнес-кейс: сверка платежей → `biz.fintech.reconciliation`

**Боль.** Клиент одним переводом оплачивает сразу два счёта, а в назначении платежа пишет «оплата по договору». Бухгалтер вручную подбирает, какие счета закрыть. При сотнях клиентов это часы работы каждый день.

**Связь с задачей.** `target` — сумма платежа, `nums` — суммы открытых счетов клиента. Ответ Two Sum — пара счетов, которую нужно закрыть.

**Правила `Reconciler`:**
1. Платёж равен одному счёту → закрыть его. Проверяется первым, это самый частый случай.
2. Платёж равен сумме двух счетов → `algos.find_pair_with_sum(...)`.
3. Иначе платёж уходит на ручной разбор: частичная оплата, переплата, опечатка.

**Бизнес-детали, которых нет в LeetCode:**
- деньги хранятся в копейках (`int`), потому что во `float` сравнение на равенство ломается;
- закрытый счёт удаляется из открытых, и второй раз его не оплатить;
- счета перебираются по сроку оплаты, поэтому при нескольких вариантах закрываются самые старые долги;
- поиск идёт только среди счетов этого клиента (`customer_id` берётся по ИНН из банковской выписки);
- реализация алгоритма выбирается флагом: `Reconciler(backend=...)`, `--backend` в демо или `ALGOS_BACKEND`.

```bash
uv run python -m biz.fintech.reconciliation.demo   # 12 платежей → 4 одним счётом, 4 парой, 4 на ручной разбор
uv run pytest tests/biz/fintech
```

**Куда развивать:** сумма из k счетов (это уже Subset Sum, NP-трудная задача, но при малых k решается через meet-in-the-middle), допуск ±N копеек на банковские комиссии, нечёткое сопоставление по назначению платежа.

## Шаг 3. Скорость

Железо: i5-13420H (8 ядер / 12 потоков, ноутбук: частоты плавают, разброс ±30%), RTX 3050 Laptop 6 GB.

### Реализации (`src/algos/_native/`, все проходят одни и те же тесты)
| backend | Как | Идея |
|---------|-----|------|
| python | dict | эталон |
| numpy | sort + `searchsorted` | без цикла на Python, O(n log n) |
| numba | `@njit`, своя хэш-таблица | открытая адресация, Fibonacci hashing, ключ и индекс рядом в памяти |
| c | `native/c/pair_sum.c` + ctypes | то же, что numba, на C, `-O3 -march=native` |
| cuda | CuPy: тот же алгоритм, что numpy | сортировка и бинарный поиск параллельно на тысячах ядер GPU |

### Один запрос (`benchmarks/two_sum_backends.py`, ndarray, пара в конце)
| n | numba | c | numpy | cuda |
|---|-------|---|-------|------|
| 100 | **5 µs** | 10 µs | 22 µs | 5.5 ms |
| 10⁴ | **160 µs** | 165 µs | 2.4 ms | 5.9 ms |
| 10⁵ | 2.3–5.7 ms | 2.6–6.6 ms | 21 ms | **5.3 ms** |
| 10⁶ | 117–162 ms | 99–217 ms | 310 ms | **17 ms** |
| 10⁷ | 1.3–1.6 s | 1.1–1.7 s | 6.5 s | **241 ms** |

- **Хэш на CPU упирается в память, а не в вычисления.** На 10⁷ получается ~120 нс на элемент: это два случайных обращения в DRAM (найти дополнение + вставить). Хранение ключа и индекса в одной ячейке дало ~15%. Дальше помогут prefetch или разбиение по хэшу, чтобы таблица помещалась в кэш.
- **У GPU фиксированная плата ~5 ms** (запуск ядер, копирование на устройство). Зато потом он в 7–10 раз быстрее CPU. Точка безубыточности около 10⁵.
- **numpy хуже хэша**: O(n log n) и случайный доступ в `searchsorted`. Векторизация не спасает плохую асимптотику. Но этот же алгоритм на GPU оказывается лучшим.
- **Вход-`list` стоит дорого**: конвертация list → ndarray на 10⁷ занимает ~0.7 s, почти столько же, сколько сам поиск. Данные стоит держать в numpy с самого начала.
- **ctypes `data_as()` стоит ~5 µs на вызов.** Замена на `c_void_p` + `.ctypes.data` срезала накладные расходы C почти вдвое.

### Много клиентов (`benchmarks/two_sum_parallel.py`), всего 2 млн счетов
`find_pairs_batch(values, offsets, targets)`: формат CSR, клиент = задача.

| стратегия | 200k × 10 | 2k × 1000 | 20 × 100k |
|-----------|-----------|-----------|-----------|
| **numba prange×12** | **20–25 ms** | **13 ms** | **12–15 ms** |
| cuda (упакованный ключ `задача<<40 \| значение`) | 27 ms | 27 ms | 30 ms |
| processes×12: python | 270–310 ms | 245–305 ms | 155–165 ms |
| threads×12: c (ctypes) | 7–8 s | 160 ms | 16 ms |
| seq: python | 1.3–1.4 s | 0.94–0.96 s | 0.45–0.47 s |
| threads×12: python | 2.5–3.4 s | 1.4–1.6 s | 380–390 ms |

Выводы:
1. **Потоки + Python бесполезны и даже вредны** из-за GIL: медленнее последовательного кода.
2. **Потоки + C работают только при крупных задачах.** GIL отпускается внутри C, но Python-цикл по клиентам его держит. На 200k мелких клиентов накладные расходы вызова (~15 µs) в 100 раз больше самой работы, плюс борьба потоков за GIL.
3. **Процессы дают честные ×4–5**, но платят за pickle и копирование данных. Без переписывания кода это лучший вариант.
4. **numba prange — победитель**: настоящие потоки без GIL, без копирования, один вызов на всю пачку. До ×70 от последовательного Python.
5. **GPU второй.** У каждого клиента мало данных, а фиксированная плата ~5 ms и копирование съедают выигрыш. GPU выиграет, когда данных на порядок больше или они уже лежат на GPU.

### Как выбирает `auto`
- `find_pair_with_sum`: cuda от 300 000 элементов → numba → c → numpy (от 10⁴) → python.
- `find_pairs_batch`: numba → cuda → numpy → python.
- Пороги — это `min_n` в `register_optional(...)`, подобранные по таблицам выше.
