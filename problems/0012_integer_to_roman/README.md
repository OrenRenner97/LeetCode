# 12. Integer to Roman

[LeetCode](https://leetcode.com/problems/integer-to-roman/) · Medium · Hash Table, Math, String

## Условие (кратко)
Перевести число 1 ≤ num ≤ 3999 в римскую запись: семь символов I V X L C D M, вычитательные формы IV, IX, XL, XC, CD, CM, не больше трёх одинаковых I/X/C/M подряд.

## Решение (solution.py): жадно по таблице из 13 номиналов

**Идея:** таблица номиналов вместе с вычитательными формами (1000 M, 900 CM, 500 D, …, 4 IV, 1 I) по убыванию. Пока число > 0, берём самый большой номинал, который в него помещается, дописываем символ, вычитаем.

**Время:** O(k · 13), где k ≤ 15 — длина ответа (на ограничениях это O(1)) · **Память:** O(1)

Корректно: на всех 3999 числах ответ — каноническая римская запись (регулярка `M{0,3}(CM|CD|D?C{0,3})…`), обратное преобразование даёт исходное число, все ответы разные.

Почему жадность здесь верна: вычитательные формы добавлены в таблицу как отдельные номиналы, и тогда каждый разряд независимо раскладывается по «своим» номиналам (900 = CM, 800 = DCCC). Без шести вычитательных пар жадность дала бы 4 = IIII.

Что можно улучшить:
- **После каждого символа поиск начинается с начала таблицы.** Для 3888 (15 символов) это ~150 проверок `num >= value` вместо 13. Остаток только убывает, значит, номиналы, которые уже не поместились, не поместятся и дальше: достаточно одного прохода по таблице (`GreedyWhile`, ×4–6).
- **Таблица создаётся на каждый вызов.** `dict` из 13 пар строится заново при каждом `intToRoman`; константа на уровне модуля — бесплатно.
- **`dict` используется как список пар:** поиск по ключу не нужен, важен только порядок (гарантирован с Python 3.7). Кортеж пар честнее говорит о намерении и итерируется чуть быстрее.
- `result += symbol` — нормально: строка ≤ 15 символов, квадратичности тут не будет.

## Шаг 1. Альтернативы (alternatives.py)

Пакет из 10⁵ чисел через `list(map(f, nums))`, Python 3.12, медиана из 5. В скобках — на один вызов.

| Подход | Время | Память | all | long (3888) | short (1000) | small (1..99) | Идея |
|--------|-------|--------|-----|------|-------|-------|------|
| Solution | O(k · 13) | O(1) | 488 ms (4.9 µs) | 985 ms | 105 ms | 352 ms | жадно, поиск с начала таблицы после каждого символа |
| GreedyDivmod | O(13) | O(1) | 178 ms | 244 ms | 81 ms | 128 ms | один проход, `divmod` даёт число повторов |
| GreedyWhile | O(13 + k) | O(1) | 125 ms | 158 ms | 63 ms | 122 ms | один проход, `while num >= value` |
| DigitTables | O(1) | O(1) | 51 ms (0.5 µs) | 54 ms | 34 ms | 36 ms | 4 таблицы по разрядам + 3 конкатенации |
| DigitPattern | O(1) | O(1) | 208 ms | 201 ms | 128 ms | 146 ms | один шаблон цифры, `str.translate` по разряду |
| **FullLookup** | O(1) | O(4000) | **8.6 ms (86 ns)** | **8.6 ms** | **15 ms** | **13 ms** | все 3999 ответов заранее |
| UnaryReplace | O(num) | O(num) | 2.2 s | 3.9 s | 1.0 s | 204 ms | "I" × num и 12 `str.replace` |

Входы: all — случайные из 1..3999; long — только 3888 (15 символов, худший для жадных); short — только 1000; small — случайные 1..99.

- **Solution проигрывает GreedyWhile в 4–6 раз только из-за возврата в начало таблицы.** На long разница максимальна (×6): 15 символов × ~10 лишних проверок. На short (один символ M) возврата нет — разрыв ×1.7, это цена создания `dict` на каждый вызов.
- **`divmod` медленнее простого `while`.** Цикл повторяется не больше трёх раз, а `divmod` — вызов функции с созданием кортежа на каждом номинале, который помещается. Плюс `symbol * count` и `"".join` дороже `+=` на 15 символах. Асимптотически GreedyDivmod лучше, на практике — нет.
- **DigitTables — лучший «честный» вариант:** 4 индекса и 3 конкатенации, без циклов. ×10 к Solution и почти не зависит от входа.
- **DigitPattern красивее, но медленнее DigitTables в 4 раза:** `str(num)`, `enumerate`, `translate` — каждое по отдельности дешёвое, но вызовов много. Обобщается на любые системы с «единицей, пятёркой, десяткой» (у нас таких нет, так что это скорее иллюстрация).
- **FullLookup — ×6 к DigitTables, ×57 к Solution:** диапазон входа крошечный (3999), таблица ~250 КБ строится один раз при импорте. 86 ns — это почти целиком цена `map` и вызова метода. Хорош, когда конвертаций много (номера глав, века, циферблаты в цикле рендера).
- **UnaryReplace** — курьёз: римская запись как сжатие унарной (IIIII → V, VV → X, …). O(num) по памяти и времени, ×250–450 к лучшему. Зато объясняет, откуда взялась система; на small (1..99) почти догоняет Solution.

## Шаг 1.5. Библиотека → `algos.to_roman`
`src/algos/arithmetic/roman.py`. Отличия от LeetCode-версии:
- **Граница явная: вне `[ROMAN_MIN, ROMAN_MAX]` = [1, 3999] → `None`.** Классическими цифрами больше не записать: символа для 5000 нет, а MMMM — уже не каноническая запись (больше трёх одинаковых подряд). Нуля и отрицательных у римлян не было. Расширения (черта над символом = ×1000, апострофус CIↃ) не стандартизованы — не поддерживаем.
- **`lowercase=True`** — строчные (`xiv`): нумерация страниц предисловия, подпунктов в документах. Таблица строчных строится лениво при первом запросе.
- **Типы:** любой целый через `operator.index` (numpy-целые тоже); `bool`, `float`, строки → `TypeError`.
- Реализация — FullLookup: таблица всех 3999 ответов строится при импорте (~4 ms) из таблиц разрядов.

Цена API, один вызов `f(1994)`, лучшее из 5:

| | время |
|-|-|
| Solution | 2.4 µs |
| DigitTables | 415 ns |
| FullLookup (без проверок) | 92 ns |
| `to_roman(n)` | **237 ns** |
| `to_roman(n, lowercase=True)` | 242 ns |

- Разница с FullLookup (×2.6) — проверка `bool`, `operator.index`, сравнение с границами и разбор keyword-аргумента. Всё равно ×10 к Solution.

Тесты `tests/algos/test_roman.py`: LeetCode-примеры, весь диапазон 1..3999 против `Solution` и против независимого обратного перевода + каноническая регулярка, границы (0, −1, 4000, 10¹⁰⁰ → `None`), строчные, numpy-целые, `TypeError`.
