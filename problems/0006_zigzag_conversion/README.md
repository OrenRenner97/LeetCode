# 6. Zigzag Conversion

[LeetCode](https://leetcode.com/problems/zigzag-conversion/) · Medium · String

## Условие (кратко)
Строка `s` (1 ≤ n ≤ 1000: буквы, `,`, `.`) записывается «зигзагом» в `numRows` строк (1 ≤ r ≤ 1000): вниз по столбцу, затем по диагонали вверх до первой строки, снова вниз. Вернуть результат, прочитанный построчно.

## Решение (solution.py): симуляция, строки в dict

**Идея:** идём по символам, держим текущую строку и направление; на краях (`0` и `r − 1`) направление меняется. Каждый символ дописывается в свою строку, в конце строки склеиваются в порядке ключей dict.

**Время:** O(n²/r) в CPython из-за `+=` (см. ниже), по замыслу O(n) · **Память:** O(n)

Корректно на всех краевых случаях, в том числе r ≥ n.

Что можно улучшить:
- **`dict_with_rows[row] += char` копирует строку целиком — отсюда квадрат.** На лимите LeetCode этого не видно, но на n = 10⁶, r = 2 решение работает **19.7 s** против 0.11 s у той же симуляции со списками (бенчмарк ниже). Лекарство — список списков и `append` + один `join` (RowsList). Почему так — разбор ниже.

### Почему `d[k] += ch` квадратичен, а `x += ch` и список — нет

Сборка строки из n символов по одному (Python 3.12):

| n | `x += "a"` (локальная) | `d[0] += "a"` (как в решении) | `append` + `join` |
|---|---|---|---|
| 10⁵ | 12 ms | 538 ms | 8 ms |
| 2·10⁵ | 15 ms | 1 736 ms | 22 ms |
| 4·10⁵ | 39 ms | **5 855 ms** | 40 ms |

При удвоении n вариант с dict замедляется в 3–3.4 раза, то есть растёт как квадрат. Два других растут линейно.

- **Строки неизменяемы.** `row + ch` создаёт новую строку длины L + 1 и копирует в неё L старых символов. Если собирать строку по символу, выходит 1 + 2 + … + L ≈ L²/2 копирований. При r = 2 это ~n²/4 на всё решение.
- **Хак CPython для локальной переменной.** Если у левой строки ровно одна ссылка и результат сразу записывается в ту же локальную переменную (`STORE_FAST`), интерпретатор расширяет строку на месте через `realloc`, и копирования нет. Это деталь реализации CPython, а не гарантия языка: в PyPy и других интерпретаторах её может не быть.
- **В `d[k] += ch` хак не срабатывает:**
  ```
  BINARY_SUBSCR      ← строка из dict на стеке: ссылок две (dict и стек)
  BINARY_OP (+=)     ← значит, нужна новая строка с полным копированием
  STORE_SUBSCR       ← запись в dict, а не в локальную переменную
  ```
- **Список линеен.** `append` кладёт только указатель, а память выделяется с запасом (~12%), поэтому в среднем это O(1). `"".join` сначала считает итоговую длину, потом один раз выделяет память и копирует каждый символ ровно один раз.

**Правило:** строку из кусков собираем в список и в конце делаем `join`. На `+=` можно полагаться только с локальной переменной в CPython, и то это оптимизация, а не гарантия.
- **`r = 1` работает случайно.** Проверка `current_row == 0` идёт раньше `== numRows − 1`, поэтому знак всегда `+1`, и строка уходит в 1, 2, 3, … Спасает ветка `else`: она создаёт новые ключи, и dict вырастает до n ключей по одному символу, а порядок вставки совпадает с исходным. Явный `if numRows == 1 or numRows >= len(s): return s` и проще, и быстрее, и делает ветку `else` ненужной.
- **`if current_row in dict_with_rows` при r ≥ 2 всегда истинно**: dict заранее заполнен всеми ключами. Если `r = 1` отсечь заранее, хватит списка `rows = [[] for _ in range(numRows)]`.
- **`index` из `enumerate` не используется**: достаточно `for char in s`.
- **Порядок строк держится на порядке вставки dict** (гарантирован с Python 3.7). Со списком это очевидно без знания этой гарантии.

## Шаг 1. Альтернативы (alternatives.py)

T = 2(r − 1) — период зигзага: r − 1 шагов вниз и r − 1 вверх.

| Подход | Время | Память | Комментарий |
|--------|-------|--------|-------------|
| **Solution (твой)** | O(n²/r) в CPython | O(n) | dict строк, `+=` по символу |
| Matrix | Θ(n·r) | Θ(n·r) | сетка как на картинке, читаем построчно, пропуская пустые клетки |
| RowsList | O(n) | O(n) | та же симуляция: списки + `append`, один `join` |
| CycleIndex | O(n) | O(n) | без симуляции: в строке `i` индексы `j·T + i` и `j·T + T − i` |
| SortByRow | O(n log n) | O(n) | строка символа `k` — `min(k mod T, T − k mod T)`, стабильная сортировка |
| SliceInterleave | O(n) | O(n) | строка `i` = срезы `s[i::T]` и `s[T−i::T]`, перемежаются через один |

### Ключевые идеи
- **Зигзаг — периодическая перестановка.** Строка символа зависит только от `k mod T`: `m ≤ r − 1` → строка `m`, иначе `T − m`. Поэтому симуляция не нужна: каждую строку можно выписать по формуле (CycleIndex) или срезом с шагом (SliceInterleave).
- **В средней строке два «потока»**: вертикальный `i, i + T, i + 2T, …` и диагональный `T − i, 2T − i, …`, и они чередуются. Первая и последняя строки — один поток (диагональный совпадает с вертикальным). Отсюда SliceInterleave: `merged[::2] = vert; merged[1::2] = diag`, вертикальный поток длиннее на 0 или 1.
- **Ответ — стабильная сортировка индексов по номеру строки** (SortByRow). Это самое короткое определение задачи, на нём же построен эталон в тестах.
- **Краевые случаи r = 1 и r ≥ n**: ответ — сама строка. При r = 1 период T = 0, поэтому формулы без этой проверки делят на ноль или зацикливаются.

**Выводы:**
- **`+=` в dict превращает O(n) в квадрат.** На r = 2 и 3 Solution растёт в ~100 раз при росте n в 10 раз (10⁵ → 10⁶: 0.24 → 19.7 s), тогда как RowsList с той же логикой — линейно. На r = n/2 строки короткие, копировать нечего, и Solution отстаёт от RowsList всего в 1.5 раза.
- **SliceInterleave быстрее всех в 5–100 раз, когда строк мало.** Python-цикла по символам нет: срезы с шагом и присваивание в срез списка выполняются на C. Время ~ n + r·(накладные на строку).
- **…и худший, когда строк много** (r = n/2): на каждую строку два среза, список и `join` ради 1–2 символов. Накладные ~1.4 µs × r съедают выигрыш. Тут лучше CycleIndex и RowsList: один проход, одно действие на символ.
- **CycleIndex не быстрее RowsList**, хотя «без симуляции»: в Python стоимость определяет число байткод-операций на символ, а не красота формулы. Его плюс в другом: индекс каждого выходного символа вычисляется независимо, это готовое ядро для numpy/C (шаг 3).
- **SortByRow** медленнее в 2–5 раз из-за `sort` с lambda-ключом, но это самое короткое корректное определение: годится как эталон.
- **Matrix** — Θ(n·r) памяти: на r = n/2 при n = 10³ уже 30× медленнее остальных. Полезен только как визуализация.
- **Что брать**: на LeetCode — RowsList (понятно, O(n)) или SliceInterleave (быстрее всех на типичных r). Для библиотеки — гибрид: срезы при малом r, формула индексов при большом.

## Шаг 1.5. Библиотека → `algos.zigzag_encode`

`src/algos/permutations/zigzag.py`:

```python
zigzag_encode(seq, rows, *, mode="zigzag") -> тот же тип       # LeetCode 6: "PAYPALISHIRING", 3 → "PAHNAPLSIIGYIR"
zigzag_decode(seq, rows, *, mode="zigzag") -> тот же тип       # обратная: decode(encode(x)) == x
zigzag_rows(n, rows, *, mode="zigzag") -> list[int]            # строка каждой позиции: [0, 1, 2, 1, 0, 1, 2]
zigzag_order(n, rows, *, mode="zigzag") -> list[int]           # перестановка: encode(x)[p] == x[order[p]]
zigzag_split(seq, rows, *, mode="zigzag") -> list[list]        # сами строки, ровно rows штук
```

Отличия от LeetCode-версии:
- **Это перестановка, и у неё есть обратная.** LeetCode просит только прямую. В библиотеке есть `zigzag_decode`: без неё не расшифровать шифр «изгородь», не собрать данные обратно после раскладки и не проверить себя (`decode ∘ encode = id` — главный тест).
- **`mode="snake"` — края дважды**: `0 1 2 2 1 0 0 1 …`, период `2·rows`. Это порядок выбора в snake-драфте и посев «змейкой» по корзинам: сильнейшие расходятся по разным группам. Устроено так же: в каждой строке два потока с шагом T, только обратный поток есть у всех строк. Для шага 2 нужен именно он.
- **Любая последовательность, тип результата = тип входа**: `str`, `bytes`, `bytearray`, `list`, `tuple`, numpy-массив (переставляется первая ось, то есть строки матрицы). Прочее (`range`, …) → `list`. Вход не меняется, изменяемый вход не возвращается как есть даже при тождественной перестановке.
- **Без `None`**: у задачи нет случая «ответа нет». Пустой вход → пустой результат того же типа. Ошибки — только в аргументах: `rows < 1` → `ValueError`, `rows` не `int` (в том числе `True`, `2.0`) → `TypeError`, неизвестный `mode` → `ValueError`.
- **Гибрид двух обходов, O(n) при любом `rows`.** SliceInterleave из шага 1 тратит ~2 µs на строку, поэтому при `rows = n/2` проигрывает даже циклу по символам. Второй обход идёт по **периодам**: вход дополняется пустышками до целого числа периодов, тогда каждая строка занимает в выходе блок одинаковой длины, и внутри одного периода позиции соседних строк идут с постоянным шагом `2·P`. Период переносится четырьмя срезами (snake — двумя), а периодов всего ~n / (2·rows). Пустышки бывают только в последнем периоде: при кодировании их убирает фильтр, при декодировании их место задаёт маска, построенная теми же срезами.
- **Одна функция переноса на оба направления**: кодирование и декодирование отличаются только флагом (откуда копировать, куда), поэтому взаимно обратны по построению.

**Порог между обходами** (n = длина, r = rows), кодирование, ms:

| n | r | по строкам | по периодам |
|---|---|-----------|-------------|
| 10³ | 15 | **0.044** | 0.086 |
| 10³ | 62 | 0.105 | **0.085** |
| 10³ | 500 | 0.93 | **0.12** |
| 10⁴ | 200 | 0.64 | 0.61 |
| 10⁴ | 5 000 | 11.5 | **1.5** |
| 10⁵ | 2 528 | 6.4 | 6.4 |
| 10⁵ | 50 000 | 89 | **14** |
| 10⁶ | 3 | **34** | 302 |
| 10⁶ | 8 000 | **46** | 92 |
| 10⁶ | 500 000 | 932 | **172** |

Строка стоит ~1.8 µs, обход по периодам добавляет ~60 ns на элемент (дополнение, фильтр, сборка списка). Значит, по строкам выгоднее, пока `1.8 µs · r < 60 ns · n`, то есть **`r ≤ n / 30`**. Точки перелома в замерах — ~30 / ~300 / ~3 000 / ~30 000, совпадают с формулой. Итог на n = 10⁶: от 23 до 170 ms на любом `rows` (было до 950 ms с одним обходом по строкам).

**Ошибки, на которых учился** (поймали тесты на тождество `decode ∘ encode` и сверку с перебором):
- у краёв zigzag обратный поток совпадает с прямым (`partner(0) = T ≡ 0`): его нельзя добавлять второй раз;
- строка с одним потоком лежит в выходе **подряд**, а не через один;
- первая версия обхода по периодам вычисляла позицию каждой пустышки в Python. При `P = 2` пустышек до n/2, и выигрыш упал с ×5 до ×1.2. Фильтр одним списковым включением и маска на срезах вернули ×5.

Тесты (`tests/algos/test_zigzag.py`) прогоняют оба обхода и `auto` на всех входах: примеры, 3000 случайных против перебора (обе моды), сверка с `RowsList` из шага 1, типы, numpy (включая матрицу), валидация и время на 10⁶.

## Шаг 2. Бизнес-кейс → `biz.edtech.railfence`

**Боль.** Платформам обучения криптографии, CTF и квестам нужны задания на классические шифры: сгенерировать, объяснить картинкой, проверить ответ, подсказать. Защитой данных «изгородь» не является: все ключи перебираются за ~0.1 s.

**Связь с задачей.** Шифр «изгородь» (rail fence) — это и есть Zigzag Conversion: `encrypt = zigzag_encode`, `decrypt = zigzag_decode`, картинка — `zigzag_rows`.

Чего нет в LeetCode:
- **сдвиг начала зигзага** (`offset`), обычный в заданиях. Через пустышки перед текстом;
- **расшифровка и картинка**;
- **взлом без ключа**: перебор всех `(rails, offset)` и ранжирование по модели пар букв (en/ru). Перестановка не меняет состав букв, поэтому различает кандидатов только порядок;
- **честная уверенность.** Нашлась настоящая неоднозначность шифра: другой сдвиг часто даёт **циклический поворот** текста, который статистика отличить не может. Повороты возвращаются отдельно, уверенность считается против лучшего не-поворота. Калибровка: от 50 символов 0 уверенных ошибок из 480 прогонов, уверенность в ~40–60% случаев.

Подробности: [`src/biz/edtech/railfence/README.md`](../../src/biz/edtech/railfence/README.md). API: `POST /v1/edtech/railfence/encrypt`, `/decrypt`, `/crack`.
