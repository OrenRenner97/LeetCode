# 4. Median of Two Sorted Arrays

[LeetCode](https://leetcode.com/problems/median-of-two-sorted-arrays/) · Hard · Array, Binary Search, Divide and Conquer

## Условие (кратко)
Два отсортированных массива `nums1` (длина m) и `nums2` (длина n). Вернуть медиану их объединения за **O(log(m + n))**.

Обозначения: N = m + n, R — диапазон значений (по условию 2·10⁶ + 1).

## Решение (solution.py): бинпоиск по разрезу

> До O(log) решение доведено **с помощью Cursor**, разбор делали вместе. План: перерешать с нуля самому **2026-11-02**.

**Идея:** искать не медиану, а **разрез**. Левая половина слитого массива — это первые `i` элементов `nums1` и первые `j = half - i` элементов `nums2`, где `half = (N + 1) // 2`. Неизвестное одно — `i`.

```
nums1:  left1 | right1      (i элементов слева)
nums2:  left2 | right2      (j = half - i элементов слева)
```

Разрез правильный, если `left1 ≤ right2` и `left2 ≤ right1`. Если `left1 > right2`, из `nums1` взяли слишком много, и `i` нужно уменьшить. Иначе взяли слишком мало, и `i` нужно увеличить. При росте `i` значение `left1` растёт, а `right2` убывает: проверка монотонна, поэтому подходит бинпоиск.

Детали:
- **`±inf` на краях**: при `i = 0` или `i = m` пустая сторона не участвует в проверке;
- **`+1` в `half`**: при нечётном N лишний элемент слева, медиана = `max(left1, left2)`;
- **обмен массивов**: бинпоиск идёт по короткому, тогда `j` всегда в `[0, n]`.

**Время:** O(log min(m, n)) · **Память:** O(1)

Что можно улучшить:
- `raise AssertionError("разрез не найден")` **недостижим вообще**, даже на неотсортированном входе. Это выяснилось на шаге 3, когда тест на «неотсортированный вход → ошибка» не смог упасть. Доказательство: если в точке `i` «взяли много» (`a[i-1] > b[j]`), то в `i - 1` «взяли мало» невозможно, потому что это было бы `b[j] > a[i-1]`. Значит, на границе `hi` никогда не «мало», на границе `lo` никогда не «много», и при `lo == hi` разрез найден. Строка — честная страховка, но ошибку на плохом входе она не ловит.
- `float("-inf")` смешивает int и float. В Python это безопасно, но в C/numba понадобится либо сигнальное значение за пределами диапазона (±(10⁶ + 1)), либо явные проверки `i == 0` / `i == m`.

## Шаг 1. Альтернативы (alternatives.py)

| Подход | Время | Память | Комментарий |
|--------|-------|--------|-------------|
| **Solution (твой)** | **O(log min(m, n))** | O(1) | разрез короткого массива |
| SortConcat | O(N log N), на деле O(N) | O(N) | `sorted(nums1 + nums2)`: Timsort видит две готовые серии и просто сливает |
| MergeFull | O(N) | O(N) | слияние из merge sort в новый список |
| MergeHalf | O(N/2) | O(1) | слияние до середины, помним только `prev` и `cur` |
| HeapqMerge | O(N/2) | O(N/2) | `heapq.merge` (C) + `islice` до середины |
| KthElement | O(log N) | O(1) | k-й элемент: сравниваем k/2-е элементы и отбрасываем k/2 за шаг |
| ValueBinarySearch | O(log R · log N) | O(1) | бинпоиск по **значению**: «сколько элементов ≤ x» через два `bisect` |

### Три разных бинпоиска
- **Solution** ищет **позицию разреза** в одном массиве. Один проход, O(log min(m, n)).
- **KthElement** ищет **k-й элемент** и выбрасывает по половине от k. Обобщается на «k-й элемент из двух массивов», но при чётном N запускается дважды.
- **ValueBinarySearch** ищет **значение** и вообще не опирается на устройство массивов: достаточно уметь считать «сколько ≤ x». Работает для любых источников с такой операцией (несколько файлов, шарды БД, k массивов), но только для дискретных значений.

### Бенчмарк (`uv run benchmarks/median_two_sorted.py`)

| вход | N | Solution | KthElement | ValueBinarySearch | SortConcat | MergeHalf | HeapqMerge | MergeFull |
|------|---|----------|------------|-------------------|------------|-----------|------------|-----------|
| перемешаны | 2 000 (лимит) | **10.7 µs** | 36 µs | 50 µs | 118 µs | 267 µs | 353 µs | 800 µs |
| перемешаны | 10⁵ | **7.9 µs** | 40 µs | 53 µs | 9.0 ms | 8.2 ms | 9.7 ms | 28 ms |
| перемешаны | 2·10⁶ | **9.9 µs** | 39 µs | 57 µs | 422 ms | 405 ms | 387 ms | 942 ms |
| не пересекаются | 2·10⁶ | **8.6 µs** | 45 µs | 48 µs | 299 ms | 325 ms | 310 ms | 513 ms |
| m = 10 | 2·10⁶ | **2.3 µs** | 33 µs | 28 µs | 310 ms | 355 ms | 328 ms | 819 ms |

- **Логарифмические решения не зависят от N**: 2 000 и 2·10⁶ стоят одинаково, около 10 µs. Линейные на 2·10⁶ медленнее в **40 000 раз**.
- **Solution в 4–5 раз быстрее KthElement**, хотя оба O(log): у KthElement два прохода при чётном N и больше ветвлений на шаг. При m = 10 разрыв ×14: Solution делает ~4 итерации по короткому массиву.
- **Даже на лимите LeetCode (N = 2 000) разрез в 11 раз быстрее `sorted`.** В задачах 1–3 на малых N встроенные функции на C обычно выигрывали; здесь O(log) против O(N) побеждает сразу.
- **Среди линейных C-шные `sorted` и `heapq.merge` обгоняют Python-слияние в 2–3 раза.** MergeHalf, которому нужна только половина, выравнивается с ними лишь на больших N.
- **SortConcat на непересекающихся массивах быстрее**: `nums1 + nums2` — уже одна отсортированная серия, Timsort проходит её за один раз.

Оговорка: меряется только вызов, массивы уже готовы. Если данные надо сначала прочитать или отсортировать, это O(N) и съедает весь выигрыш. O(log) ценен там, где отсортированные данные **уже лежат** в памяти или в индексе и медиану спрашивают много раз.

## Шаг 1.5. Библиотека → `algos.median_of_sorted`

`src/algos/binary_search/sorted_union.py`:

```python
median_of_sorted(*arrays, check_sorted=False) -> float | Decimal | None      # медиана объединения
kth_of_sorted(*arrays, k, check_sorted=False) -> T | None                   # k-й (перцентиль), сам выбирает алгоритм
kth_of_two_sorted(a, b, k, check_sorted=False) -> T | None                  # k-й (с нуля) из двух
kth_of_many_sorted(arrays, k, check_sorted=False) -> int | None             # k-й из любого числа, только целые
```

Отличия от LeetCode-версии:
- **`None` вместо гарантий**: все массивы пустые или `k` вне диапазона → `None`;
- **k-й элемент, а не только медиана**: разрез обобщён с «половины» на любое `need`. Отсюда любые перцентили: p95 = `kth(..., ceil(0.95·N) - 1)`;
- **любые сравнимые типы** для одной-двух последовательностей: `Decimal`, `str`, кортежи, numpy. Для этого `±inf` заменены явными проверками краёв (`i > 0`, `j < n`): `float("-inf")` нельзя сравнить со строкой;
- **тип результата следует за входом**: медиана всегда считается как `(x + y) / 2`, даже при нечётной длине (`x = y`). Поэтому int → float, а `Decimal` → `Decimal` без потери копеек;
- **три и больше последовательности**: `ValueBinarySearch` из шага 1, только для целых. Тип проверяется по краям массивов, а не по всем элементам: полная проверка стоила бы O(n);
- **сортированность не проверяется по умолчанию**: проверка — O(n) и убивает смысл O(log). Флаг `check_sorted=True` включает её для данных извне. Без флага неотсортированный вход даёт мусорный ответ, но **никогда не исключение**: разрез существует для любого входа (см. «Что можно улучшить» выше);
- **numpy**: `searchsorted` вместо `bisect`, края приводятся к Python `int`, иначе `(lo + hi)` переполнит int64.

Замеры:
- две последовательности по 10⁶: `median_of_sorted` 7.8 µs против 6.8 µs у `Solution`. Обобщение почти бесплатно;
- 100 numpy-шардов по 10⁵ (всего 10⁷): **9.7 ms** против **147 ms** у `np.median(np.concatenate(...))`, ×15. При этом ничего не копируется.

## Шаг 2. Бизнес-кейс: справедливая цена по площадкам → `biz.fintech.fair_price`

**Боль.** Бумага торгуется на нескольких биржах, на ОТС и у брокеров. Для оценки позиций и контроля нерыночных сделок нужна одна справедливая цена. Средняя ломается от одного сбойного фида.

**Связь с задачей.** У каждой площадки лента сделок за окно, **уже отсортированная по цене**. Справедливая цена — медиана объединения лент, коридор — квартили p25 и p75. Всё это k-й элемент объединения отсортированных массивов **без слияния**: `algos.kth_of_sorted`. Для двух площадок работает твой разрез, для трёх и больше — бинпоиск по значению.

| Правило | Смысл |
|---------|-------|
| `window=5 мин` | участвуют только свежие сделки |
| `stale_after=30 с` | площадка без сделок дольше → `stale`, фид завис |
| `max_venue_deviation_bps=100` | медиана площадки дальше 1% от общей → `outlier` |
| `min_venues=2` | меньше площадок → `insufficient`; после отсева выбросов → `disputed` |
| `tolerance_bps=200` | своя сделка дальше 2% от справедливой → `off_market` |

Что дало обобщение из шага 1.5:
- **k-й элемент, а не только медиана** — отсюда коридор p25–p75;
- **сколько угодно последовательностей** — сколько угодно площадок;
- **`None` вместо гарантий** превращается в бизнес-статусы `insufficient` и `disputed`: лучше не опубликовать цену, чем опубликовать неверную.

Бизнес-детали: цены в копейках, медиана чётного числа сделок округляется по-банковски, отклонения сравниваются в целых числах. Лента площадки (`VenueTape`) держит сделки и по времени (для окна), и по цене (для бинпоиска), поэтому сортировать на каждый запрос не нужно. Подробности и «что взяли бы в проде» (медиана, взвешенная по объёму): [`src/biz/fintech/fair_price/README.md`](../../src/biz/fintech/fair_price/README.md). API: `POST /v1/fintech/fair-price`.

```bash
uv run python -m biz.fintech.fair_price.demo   # сбой фида ×100: средняя 2 763 ₽, медиана 285.43 ₽; две площадки на 3% → disputed
```

Нативные backend'ы принимают только **целочисленные numpy-массивы**. Списки, `Decimal`, float и срезы с шагом идут в `python`, даже если backend указан явно (правило 4 из `_native/README.md`).

**K шардов, бинпоиск по значению** (`kth_of_many_sorted`, медиана):

| K × L | c | numba | python | `np.median(np.concatenate)` |

**Выводы:**
- **Для O(log) вызов дороже работы.** Ядро разреза в numba стоит 0.8 µs, а публичная функция — 4.7 µs. Остальное съедают проверка входа (`_as_int64` ~1.2 µs), режим `auto` (`os.environ.get` отсутствующей переменной ~1.2 µs) и распаковка результата. Итог ×2.6, а не ×20.
- **C проиграл numba на разрезе**, хотя ядро не медленнее: `a.ctypes.data` стоит ~1.6 µs на массив, плюс `byref`.
- **На K шардах C выиграл у numba** (×1.4–3.5): массив указателей дешевле, чем `numba.typed.List` (~2 µs на массив).
- **Бинпоиск без ветвлений** (cmov) быстрее обычного до ×2.7. Две гипотезы не подтвердились: что ветвления помогают предзагрузке памяти и что помогает сужение окна поиска.
- **1000 мелких шардов — единственный случай, где `np.median(np.concatenate)` почти догоняет** (10 ms против 3.5 ms у C). Данных всего 8 MB, и O(N) на C работает быстрее, чем 1000 × 31 бинпоиск с обвязкой на каждый массив.
- **Бизнесу нативный код не понадобился.** Цены лежат в узком диапазоне (±20 копеек → ~6 итераций), и Python на списках (26 µs) сравнялся с C на numpy (22 µs), а конвертация в numpy стоит 500 µs. Выигрыш −25% дала бизнес-оптимизация: без выбросов медиана не пересчитывается второй раз.
- Попутно выяснилось: **`raise` в разрезе недостижим** (см. «Что можно улучшить»). Тест «неотсортированный вход → ошибка» просто не смог упасть.

**Как выбирает `auto`:** разрез — `numba → c → python`; K шардов — `c → numba → python`; `min_n = 0` (нативные выигрывают на любом размере, если вход уже numpy). Не numpy → всегда `python`.

**Куда развивать:** пакетный режим (справедливая цена по тысячам бумаг за один вызов, `prange`); медиана, взвешенная по объёму (бинпоиск по значению с префиксными суммами объёмов).
