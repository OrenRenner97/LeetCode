# 11. Container With Most Water

[LeetCode](https://leetcode.com/problems/container-with-most-water/) · Medium · Array, Two Pointers, Greedy

## Условие (кратко)
Массив `height` из n ≤ 10⁵ высот (0 ≤ h ≤ 10⁴). Выбрать две линии i < j с наибольшей площадью `(j − i) · min(h[i], h[j])`.

## Решение (solution.py): два указателя с краёв

**Идея:** начинаем с самого широкого контейнера (0, n − 1). Площадь ограничена низкой стенкой, поэтому сдвигаем её внутрь: с этой стенкой любой более узкий контейнер не лучше текущего (ширина меньше, высота не больше её). Высокую стенку сдвигать бессмысленно по той же причине. За n − 1 шаг указатели встречаются.

**Время:** O(n) · **Память:** O(1)

Корректно: сверено с перебором на 3 тыс. случайных массивов (в том числе с большим числом равных высот) и с альтернативами на пяти массивах по 10⁵.

Почему это не жадность «на удачу» (на собеседовании спросят): отбрасываемая на шаге пара — это все контейнеры с низкой стенкой `left` и правой границей внутри `(left, right)`. У каждого из них ширина < `right − left`, а высота ≤ `h[left]`, значит, площадь ≤ текущей. Ни одна пара с ответом не теряется.

Что можно улучшить:
- **Решение в 3 раза медленнее, чем могло бы быть, из-за `max()` и `min()`.** Алгоритм оптимален, но каждый шаг — два вызова встроенных функций, а это самое дорогое в цикле CPython. С `if` вместо них (`TwoPointersInline`) — ×3 быстрее, ничего не меняя в идее.
- **Равные высоты** обрабатываются корректно: при `h[left] == h[right]` двигается правый, и ответ не теряется. Сдвигать при равенстве можно любой: контейнер с любой из двух стенок и меньшей шириной не лучше текущего.
- **Пропуск низких линий** (`TwoPointersSkip`) — ещё ×3: после сдвига линии не выше только что отброшенной стенки дать больше не могут, площадь для них можно не считать.

## Шаг 1. Альтернативы (alternatives.py)

| Подход | Время | Память | random 10⁵ | increasing 10⁵ | equal 10⁵ | hill 10⁵ | Идея |
|--------|-------|--------|------|------|------|------|------|
| Solution | O(n) | O(1) | 97 ms | 133 ms | 97 ms | 111 ms | два указателя, `max`/`min` |
| BruteForce | O(n²) | O(1) | — | — | — | — | все пары; 10³ — 110–155 ms, 10⁵ — ~20 минут |
| TwoPointersInline | O(n) | O(1) | 32 ms | 28 ms | 36 ms | 45 ms | то же, `if` вместо вызовов |
| **TwoPointersSkip** | O(n) | O(1) | **11 ms** | **18 ms** | **15 ms** | **21 ms** | пропуск линий не выше отброшенной стенки |
| SortByHeight | O(n log n) | O(n) | 171 ms | 63 ms | 56 ms | 68 ms | от высоких к низким, самая дальняя из пройденных |
| NumpySortByHeight | O(n log n) | O(n) | 55 ms | 30 ms | 16 ms | 26 ms | то же: `argsort` + `minimum/maximum.accumulate` |

Один вызов, Python 3.12, медиана из 5. Входы: random — равномерно [0, 10⁴]; increasing — `i · 10⁴ // n` (плато по 10 одинаковых); equal — все 10⁴; hill — низко по краям, высоко в середине.

- **Главный выигрыш — не в алгоритме, а в цене строки CPython.** Все три варианта с двумя указателями — один и тот же O(n), а разброс ×9. Вызовы `max()`/`min()` (Solution → Inline, ×3) и лишние умножения на заведомо проигрышных линиях (Inline → Skip, ×1.5–3).
- **TwoPointersSkip сильнее всего на random:** после высокой стенки большинство следующих линий ниже неё, и их пропускает короткий цикл сравнений без умножений и без обновления максимума. На строго возрастающем входе пропускать нечего — при n = 10³ (шаг высоты 10, плато нет) Skip медленнее Inline из-за лишнего сравнения.
- **Сортировка по высоте — другой и тоже верный взгляд**: пара считается, когда обрабатывается её более низкая линия, а партнёр — самый дальний среди более высоких (накопленные min/max индексов). O(n log n), в Python медленнее, но **векторизуется**: NumpySortByHeight обгоняет Solution в 2–6 раз, хотя асимптотически хуже. Два указателя на numpy не ложатся: каждый шаг зависит от предыдущего.
- **numpy не догнал Skip** даже на 10⁵: `argsort` — это n log n сравнений, а Skip делает ~n дешёвых шагов. На равных высотах они почти сравнялись (сортировка уже упорядоченного массива быстрая).
- **BruteForce** — только как эталон: 10³ элементов — 0.1 s, на 10⁵ было бы ~20 минут.

## Шаг 1.5. Библиотека → `algos.max_container`
`src/algos/two_pointers/container.py` (новая техника `two_pointers/`). LeetCode 11 = `max_container(height).area`. Отличия от LeetCode-версии:
- **Возвращает пару**, а не только площадь: `Container(left, right, area)`. Пары нет (n < 2 или все уже `min_width`) → `None`. Нулевая площадь — это пара с `area = 0`, а не `None`.
- **`xs` — произвольные координаты линий** (столбы вдоль дороги, станции): площадь `(xs[j] − xs[i]) · min(h)`. Доказательство двух указателей от этого не меняется: сдвиг внутрь только уменьшает ширину.
- **`min_width`** — только достаточно широкие пары. Два указателя остаются верными: ширина при сдвигах только убывает, поэтому, как только пара уже `min_width`, все оставшиеся тоже — цикл останавливается.
- **int и float**, numpy-массивы (переводятся в list: поэлементный доступ к ndarray в Python в ~10 раз дороже).
- **Валидация**: длины, высоты ≥ 0 и конечные, `xs` строго возрастают, `bool` не число.
- Реализация — TwoPointersSkip; лучшее держится в локальных переменных, `Container` создаётся один раз в конце.

Цена API, n = 10⁵, random (медиана из 25, вперемешку):

| | время |
|-|-|
| Solution | 59 ms |
| `max_container(h)` (int) | **15 ms** |
| `max_container(h)` (float) | 16 ms |
| `max_container(h, xs)` | 22 ms |
| TwoPointersSkip (без валидации) | 6.7 ms |

- **Валидация стоила дороже алгоритма.** Первая версия проверяла каждый элемент в Python-цикле (`isinstance`, `< 0`, `isfinite`) и шла 32 ms — в 4 раза медленнее голого алгоритма. Переписал на C-уровневые проходы: `set(map(type, h))`, `min(h)`, `all(map(isfinite, h))` только если есть float, возрастание `xs` — `all(map(operator.lt, x, islice(x, 1, None)))`. Стало 15 ms; оставшиеся ×2.2 к Skip — это три лишних прохода по 10⁵ элементов, честная цена контракта.
- **`best` в локальных переменных вместо `NamedTuple`** — ещё ~25%: атрибут `best.area` и создание кортежа на каждом улучшении в цикле CPython заметны.
- Замеры на ноутбуке шумят (один и тот же Skip показывал 7 и 16 ms в соседних запусках), поэтому финальные цифры — медиана из 25 прогонов вперемешку.

Тесты `tests/algos/test_container.py`: LeetCode-примеры и 500 массивов против `Solution`, 3 тыс. случайных против перебора (с `xs` и `min_width`; проверяется, что возвращённая пара действительно даёт свою площадь), float, `None`-случаи, numpy и 10⁵, валидация.
