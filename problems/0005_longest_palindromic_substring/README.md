# 5. Longest Palindromic Substring

[LeetCode](https://leetcode.com/problems/longest-palindromic-substring/) · Medium · Two Pointers, String, Dynamic Programming

## Условие (кратко)
Строка `s` (1 ≤ n ≤ 1000, буквы и цифры). Вернуть самую длинную **подстроку**-палиндром. Если таких несколько, подойдёт любая.

## Решение (solution.py): перебор всех подстрок

**Идея:** для каждой пары `i ≤ j` взять `s[i:j+1]`, сравнить с разворотом и запомнить самую длинную.

**Время:** Θ(n³): n²/2 подстрок, и на каждую срез + разворот + сравнение за O(n) · **Память:** O(n) на срезы

Корректно: при равных длинах условие `>` оставляет самую левую подстроку.

Что можно улучшить:
- **Кубическое время на лимите — около 0.55 s на одну строку длины 1000** (бенчмарк ниже). На LeetCode это на грани TLE: в наборе десятки тестов.
- **`s[i:j+1]` строится три раза**: для проверки, для разворота и для ответа. Хватит одного раза: `sub = s[i:j+1]`, затем `sub == sub[::-1]`.
- **Нет отсечения**: подстроки не длиннее `max_length` проверять бессмысленно, поэтому внутренний цикл можно начинать с `j = i + max_length`. Срезы останутся, но их станет заметно меньше.
- **Вложенные `if`** (проверка палиндрома и сравнение длины) можно склеить через `and` (ruff SIM102).
- **Палиндром проверяется с нуля**, хотя `s[i..j]` — палиндром тогда и только тогда, когда `s[i] == s[j]` и `s[i+1..j-1]` — палиндром. На этом наблюдении построены все решения O(n²) ниже.

## Шаг 1. Альтернативы (alternatives.py)

| Подход | Время | Память | Комментарий |
|--------|-------|--------|-------------|
| **Solution (твой)** | Θ(n³) | O(n) | все подстроки + проверка срезом |
| LongestFirst | O(n³), лучший случай O(n) | O(n) | длины от n вниз, первая найденная — ответ |
| DPTable | Θ(n²) | O(n²) | `dp[i][j] = s[i] == s[j] and dp[i+1][j-1]` |
| ExpandAroundCenter | O(n²) | O(1) | 2n − 1 центров (символы и промежутки), расширяемся, пока края равны |
| GrowByTwo | O(n²) в худшем | O(n) | ответ растёт максимум на 2 за шаг: на каждом `i` две проверки срезом |
| HashBinarySearch | O(n log n) | O(n) | бинпоиск по длине отдельно для чётных и нечётных + полиномиальные хэши |
| Manacher | **O(n)** | O(n) | радиус зеркального центра внутри самого правого палиндрома |

### Ключевые идеи
- **Палиндром строится от центра.** Центров всего 2n − 1, поэтому O(n²) пар превращаются в O(n) центров × длина расширения. Это и есть ExpandAroundCenter, стандартный ответ на собеседовании.
- **GrowByTwo**: если палиндром, кончающийся в `i`, длиннее текущего `best`, то он длиннее ровно на 1 или 2. Если срезать с него по символу с краёв, получится палиндром, кончающийся в `i − 1`, а он не длиннее `best`. Поэтому на каждом `i` проверяются всего две подстроки, и сравнение срезов идёт на C.
- **Монотонность только внутри чётности.** Из палиндрома длины L следует палиндром длины L − 2, но не L − 1: в `"aba"` нет палиндрома длины 2. Поэтому HashBinarySearch запускает два бинпоиска.
- **Manacher**: `"^#a#b#a#$"` делает все палиндромы нечётными, а сторожа `^`/`$` убирают проверки границ. Внутри самого правого известного палиндрома радиус в точке `i` не меньше радиуса в зеркальной точке `2c − i` (с обрезкой по границе). Правая граница `r` только растёт, поэтому сравнений всего O(n).
- **Ловушка**: «LCS строки и её разворота» не работает. В `"abacdfgdcaba"` общая подстрока `"abacd"` не палиндром. Этот случай есть в тестах.

| random | 1 000 (лимит) | 539 ms | 434 ms | 80 ms | **1.1 ms** | **1.0 ms** | 21 ms | 2.0 ms |
| random | 10⁴ | — | — | — | **11 ms** | **11 ms** | 461 ms | 31 ms |

| binary | 1 000 | 565 ms | 506 ms | 106 ms | **1.1 ms** | **1.1 ms** | 19 ms | 2.9 ms |
| binary | 10⁵ | — | — | — | — | **131 ms** | 4.1 s | 239 ms |

| same | 10⁵ | — | — | — | — | 9.4 s | **218 ms** | 356 ms |

**Выводы:**
- **Solution на лимите в 500 раз медленнее лучших.** Θ(n³) не спасают даже срезы на C. LongestFirst почти не помогает на случайных строках, зато мгновенен на `"aaa…"`: первая же проверка — вся строка.
- **На обычных строках побеждают «квадратичные» ExpandAroundCenter и GrowByTwo.** Когда ответ короткий, расширение от центра останавливается через 1–2 шага, и в среднем это O(n). Manacher честно делает O(n), но с бо́льшей константой (сборка `t`, массив `p`, `max` по парам) и проигрывает в 2–3 раза.
- **На `"aaa…"` квадрат проявляется**: ExpandAroundCenter на 10⁴ — 11 s, GrowByTwo на 10⁵ — 9.4 s (срезы растут до n, хоть и на C). Гарантию дают только Manacher и HashBinarySearch.
- **HashBinarySearch — лучший на `"aaa…"` и худший на случайных строках.** Когда ответ длинный, первая же позиция совпадает и `find` выходит сразу. Когда ответ короткий, каждая проверка длины проходит всю строку: ~2 log n полных проходов с арифметикой по модулю в Python.
- **DPTable — худший из O(n²)**: всегда n²/2 клеток, без раннего выхода, и O(n²) памяти. На 10⁴ это ~800 МБ указателей.
- **Что брать**: на LeetCode — ExpandAroundCenter (просто и быстро). Для произвольных и враждебных данных — Manacher: единственный с гарантией O(n) без хэшей и вероятностей.

## Шаг 1.5. Библиотека → `algos.longest_palindrome`

`src/algos/palindromes/manacher.py`:

```python
palindrome_radii(seq, *, mirror=None) -> list[int]                                   # 2n + 1 центров → длина максимального палиндрома
longest_palindrome(seq, *, mirror=None) -> tuple[int, int] | None                    # [start, end) самого длинного
maximal_palindromes(seq, *, min_length=2, mirror=None) -> list[tuple[int, int]]      # все максимальные длины ≥ min_length
```

Отличия от LeetCode-версии:
- **Manacher, а не расширение от центра**: в бенчмарке шага 1 расширение быстрее на обычных строках, но на `"aaa…"` у него O(n²) (11 s на 10⁴). Для библиотеки важнее гарантия: данные извне бывают враждебными. Тест `test_linear_on_worst_case` проверяет `"a" * 200 000`.
- **Индексы вместо подстроки**: `[start, end)`, как у `longest_unique_window`. Вызывающий сам решает, делать ли срез.
- **Самый левый из самых длинных**: контракт однозначен, LeetCode допускал любой.
- **`None` вместо гарантий**: пустой вход или ни одного палиндрома (возможно только с `mirror`) → `None`.
- **Любая последовательность**: строки, списки чисел, кортежи, numpy (переводится в список: поэлементная индексация ndarray в Python дорогая).
- **`mirror` — палиндром с отображением**: слева должен стоять `mirror[элемент справа]`. Для ДНК это обратная комплементарность: `GAATTC` (сайт EcoRI) — палиндром, хотя как строка он не симметричен. Отображение обязано быть **инволюцией** (`mirror[mirror[x]] == x`, иначе `ValueError`): только тогда отражение внутри палиндрома даёт правильный стартовый радиус, и O(n) сохраняется. Элемент без пары (например, `N` в ДНК) не совпадает ни с чем. Нечётный палиндром возможен, только если центр переходит сам в себя.
- **Без строки-обёртки `"^#a#b#$"`**: на чётных позициях виртуальной строки стоят разделители, они всегда равны друг другу, поэтому элементы сравниваются только на нечётных позициях. Работает для любых элементов, а не только для символов, и не требует сторожей, которых нет в данных.
- **`palindrome_radii` — основа для остального**: по нему за O(n) считаются и самый длинный, и все максимальные палиндромы, и число палиндромных подстрок (LeetCode 647: сумма `(L + 1) // 2` по центрам).

Замеры (n = 10⁵): библиотека 196 ms на случайной строке и 296 ms на `"aaa…"` против 179 и 264 ms у учебного Manacher. Универсальность (произвольные элементы, проверки чётности) стоит 10–25%. С `mirror` на ДНК — 139 ms: нечётные центры пропускаются сразу.

## Шаг 2. Бизнес-кейс → `biz.biotech.cloning`

**Боль.** При клонировании ДНК перед каждым экспериментом нужно знать, где режут ферменты рестрикции, чем открыть вектор, не задев вставку, какие полосы покажет гель и не слипнется ли праймер сам с собой. Ошибка обнаруживается только через дни работы.

**Связь с задачей.** Сайт фермента рестрикции II типа (EcoRI — `GAATTC`) — **палиндром относительно комплемента**: обе цепи ДНК читаются одинаково. Это ровно `mirror` из шага 1.5. Один проход Манакера находит все палиндромные центры, и сайты всего каталога проверяются только на них, по словарю: время почти не зависит от числа ферментов. Самокомплементарный участок праймера — это самый длинный палиндром с комплементом, то есть сама задача 5.

Чего нет в LeetCode:
- **кольцевая ДНК**: сайт через «начало» плазмиды;
- **несколько ферментов на одном центре**: изошизомеры (SmaI/XmaI) и вложенные сайты (MspI в SmaI);
- **концы и совместимость**: 5'/3'/тупые, выступ (BamHI и BglII сшиваются);
- **3'-конец праймера** опаснее середины: отдельный порог для палиндрома, касающегося конца (`maximal_palindromes`).

Демо: вектор 3 000 п.н. с полилинкером на 8 ферментов. EcoRI в кандидаты **не попал**, потому что в «случайном» остове нашёлся второй сайт. Ровно так выглядит настоящая ошибка, которую ловит модуль. Геном 500 000 п.н. по 26 ферментам — 0.8 s на Python, 0.11 s после шага 3.

Подробности: [`src/biz/biotech/cloning/README.md`](../../src/biz/biotech/cloning/README.md). API: `GET /v1/biotech/cloning/enzymes`, `POST /v1/biotech/cloning/restriction-map`, `/candidates`, `/primer-check`.

## Шаг 3. Скорость (`uv run benchmarks/longest_palindrome_backends.py`)

Нативные backend'ы `numba` и `c` для `palindrome_radii`, а через неё и для `longest_palindrome` / `maximal_palindromes`. Вход кодируется в `_native/mirror_codes.py`: строка → кодовые точки int32 через UTF-32 (без цикла на Python), отображение → таблица по коду, `a[lo] == b[hi]` вместо `seq[lo] == mirror[seq[hi]]`. Массив целых идёт как есть (без `mirror`).

`palindrome_radii`, полный вызов (кодирование входа + ядро + `tolist`):

| вход | n | python | numba | c |
|------|---|--------|-------|---|
| буквы | 20 | 24 µs | **20 µs** | 39 µs |
| буквы | 2 000 | 3.0 ms | **118 µs** | 126 µs |
| буквы | 10⁶ | 1.62 s | 95 ms | **47 ms** |
| `"aaa…"` | 10⁶ | 2.54 s | 211 ms | **143 ms** |
| ДНК + комплемент | 20 | **25 µs** | 53 µs | 42 µs |
| ДНК + комплемент | 200 | 259 µs | **44 µs** | 59 µs |
| ДНК + комплемент | 10⁶ | 1.24 s | **50 ms** | 57 ms |

Из чего складываются ~50 ms на ДНК 10⁶: `encode` 8 ms, **ядро 22 ms**, `radii.tolist()` 28 ms.

Бизнес целиком (`find_sites`, 26 ферментов): 10⁴ п.н. — 13.1 ms → **1.6 ms** (×8); 10⁶ п.н. — 1.59 s → **0.15 s** (×10). `check_primer` на 23 п.н.: Python 50 µs против 82 µs у нативных, поэтому `auto` для праймеров остаётся на Python.

**Выводы:**
- **Ядро даёт ×25–35, вызов целиком — ×15–35.** Ядро стоит 22 ms на 10⁶, а `tolist()` результата — ещё 28 ms. Поэтому `longest_palindrome` и `maximal_palindromes` разбирают ndarray сами (`argmax`, фильтр + `argsort`) и не делают `tolist` всего массива.
- **numba и C равны по ядру** (разница ±1.5× плавает от прогона к прогону на ноутбуке). numba первая: у неё дешевле вход, C — запасной вариант без numba.
- **Переписать цикл расширения в индексах элементов (без проверки чётности) не помогло** ни в C, ни в numba: компилятор и так хорошо его разворачивает. Оставлена простая версия.
- **Закон Амдала в бизнесе.** После ускорения ядра `find_sites` на 10⁶ дал только ×5 (285 ms): Python-цикл шёл по всем 2·10⁶ радиусам. Помогли три бизнес-правки, а не алгоритм: (1) `maximal_palindromes` с векторным фильтром — в Python приходят только ~1/16 центров; (2) `Site` — `NamedTuple` вместо frozen dataclass (создание в 4 раза дешевле, сайтов ~24 тысячи); (3) проверка алфавита `re.fullmatch` вместо `set(seq)` (42 → 10 ms). Итого 285 → 150 ms.
- **На коротких входах с `mirror` Python быстрее**: построение таблицы комплемента и вход в JIT стоят ~30–50 µs, а праймер — 20 символов.

**Как выбирает `auto`:** `priority = ("numba", "c", "python")`, `min_n = 64` для обоих нативных. Нативные выбираются только для строки или ndarray целых без `mirror`; список произвольных объектов → `python` (явный нативный backend на нём → `TypeError`).
