# 2. Add Two Numbers

[LeetCode](https://leetcode.com/problems/add-two-numbers/) · Medium · Linked List, Math, Recursion

## Условие (кратко)
Два числа записаны связными списками цифр в обратном порядке (младший разряд первым). Вернуть их сумму в том же формате.

## Решение (solution.py)
**Идея:** сложение столбиком. Идём по обоим спискам одновременно, складываем цифры и перенос, младший разряд записываем, перенос несём дальше. Фиктивная голова `dummy` убирает отдельный случай «первого узла».
**Время:** O(max(m, n)). **Память:** O(1) дополнительно + O(max(m, n)) на ответ.

Это уже оптимум по асимптотике: прочитать все цифры обязательно, и ответ такой длины тоже обязателен.

Мелочи, которые можно упростить (см. `Compact`):
- `carry, digit = divmod(total, 10)` вместо `if total > 9`. Работает для любого основания, не только для 10;
- `while l1 or l2 or carry`: финальный перенос обрабатывается внутри цикла, и отдельный `if carry` после цикла не нужен.

## Шаг 1. Альтернативы (alternatives.py)

| Подход | Время | Доп. память | Когда лучше |
|--------|-------|-------------|-------------|
| **Solution (твой)** | O(max(m,n)) | O(1) + ответ | **по умолчанию** |
| Compact | O(max(m,n)) | O(1) + ответ | то же, короче, на ~15% быстрее |
| ViaInt | O(n²)* | O(n) | никогда в проде; ок в Python для коротких чисел |
| Recursive | O(max(m,n)) | O(max(m,n)) стек | функциональный стиль, короткие числа |
| InPlace | O(max(m,n)) | **O(1) всего** | вход больше не нужен, и важна память/GC |

\* `int(str)` и `str(int)` в CPython квадратичны по числу цифр.

### Почему «через int» — ловушка
- В C++, Java или Go 100 цифр не влезут ни в какой встроенный тип, будет переполнение. Задача специально про это.
- В Python int бесконечной длины, **но** с Python 3.11 конвертация int ↔ str ограничена 4300 цифрами (защита от DoS, CVE-2020-10735). Проверено: на 5000 цифрах `ValueError`.
- Работает за O(n²) вместо O(n).

### Рекурсия
Красиво читается, но каждый разряд — это кадр стека. Лимит Python ~1000 кадров: на 2000 цифрах проверено, получаем `RecursionError`. Под ограничения LeetCode (≤ 100) проходит.

### InPlace: trade-off память ↔ безопасность
Сумма записывается прямо в узлы `l1`, а когда `l1` кончается, продолжаем в хвосте `l2`. Новый узел создаётся максимум один (под финальный перенос). Цена: **входные списки испорчены**. В библиотечной функции так делать нельзя без явного флага, а внутри своего конвейера можно, если вход больше никому не нужен.

## Шаг 1.5. Библиотека → `algos.add_digits`

`src/algos/arithmetic/digits.py`:

```python
add_digits(a, b, *, base=10, backend=None) -> list[int]   # младший разряд первым
to_digits(n, base=10) / from_digits(digits, base=10)      # int ↔ цифры
```

Отличия от LeetCode-версии:
- **массив вместо связного списка**: список — формат условия, а не удобная структура данных. Массив можно отдать numpy, C и GPU;
- **`base`**: десятичная система — частный случай. С `base=2**32` это лимбы (limbs), так устроены BigInt в GMP/CPython и `uint256` в Ethereum;
- **нормализация**: без ведущих нулей на выходе, при этом вход с ведущими нулями и пустой вход (= 0) принимаются;
- **валидация**: цифра вне `[0, base)` или `base < 2` → `ValueError`;
- **ранний выход по хвосту**: когда перенос погас, остаток длинного числа копируется срезом, без цикла на Python.

| 10⁶ десятичных цифр | Время |
|---------------------|-------|
| Solution: связный список (+1.8 s на построение двух списков) | 1.21 s |
| `add_digits(base=10)` на list | 0.27 s |
| то же число в `base=2**32` (~111k лимбов) | **0.05 s** |

Чем больше основание, тем меньше цифр и итераций. Это главный трюк длинной арифметики: компьютер складывает 32/64-битные слова, а не десятичные цифры.

## Шаг 2. Бизнес-кейс: учёт токена на uint256 → `biz.crypto.ledger`

**Боль.** В Ethereum балансы хранятся в `uint256`, в минимальных единицах: 1 ETH = 10¹⁸ wei. В int64 помещается всего ~9.2 ETH, а float теряет копейки, то есть wei. Любой бэкенд биржи, кошелька или индексатора обязан считать в 256 битах и при этом вести себя как смарт-контракт: переполнение — это ошибка, а не «большое число».

**Связь с задачей.** `UInt256` — это 4 лимба по 64 бита, младший первым: ровно формат LeetCode 2, только `base = 2**64`. Сложение — это `add_digits`, вычитание — `sub_digits` (добавлен в библиотеку: заём вместо переноса). Если перенос вылез в 5-й лимб, это переполнение.

**Что умеет модуль:**
- `UInt256`: `+`, `-`, сравнение, `hex()`; переполнение и уход ниже нуля дают исключение, как `panic 0x11` в Solidity ≥ 0.8;
- `parse_units("1.5", 18)` / `format_units`: перевод между ETH и wei **только из строк**, float запрещён (`TypeError`);
- `Ledger` (ERC-20-подобный): `mint` / `burn` / `transfer`, журнал событий `Transfer`, `audit()` проверяет инвариант Σ балансов == `total_supply`;
- **атомарность**: сначала считаются все новые значения, потом записываются. Если на любом шаге ошибка, состояние не меняется (как `revert` в EVM);
- адреса: проверка формата `0x` + 40 hex, регистр приводится к нижнему.

```bash
uv run python -m biz.crypto.ledger.demo
uv run pytest tests/biz/crypto
```

Тесты: 500 случайных операций `UInt256` против Python int, атомарность при нехватке баланса и при переполнении, 2000 случайных mint/burn/transfer против эталона на обычных int с проверкой инварианта.

**Честно: зачем лимбы, если в Python int и так бесконечный?**
1. Нужна точная семантика EVM: потолок 2²⁵⁶ и проверяемая арифметика.
2. **Фиксированные лимбы — это формат для векторизации.** Миллион балансов — это массив `(N, 4) uint64`, который можно отдать numpy, numba и GPU. С Python int так нельзя. Это и будет шаг 3.

**Куда развивать:** `approve` / `transferFrom` (allowance), умножение и деление `uint256` (для расчёта комиссий и курсов), индексатор, который восстанавливает балансы из журнала событий блокчейна.

## Шаг 3. Скорость

`uv run benchmarks/add_two_numbers_backends.py`. Железо: i5-13420H (12 потоков), RTX 3050 Laptop. Ноутбук, разброс ±30%.

### Три способа победить перенос

Перенос выглядит строго последовательным: разряд k ждёт разряд k−1. Есть три классических способа с этим справиться, все из схемотехники процессоров:

| Способ | Где | Идея |
|--------|-----|------|
| **Ripple carry + ADC** | `native/c/digits.c` | честно последовательно, но инструкцией `adc`: процессор сам несёт перенос через флаг CF, 64 бита за такт |
| **Carry-select** | `numba_impl._add_digits_par` | каждый поток складывает свой кусок, считая что переноса на входе нет; короткий скан по кускам; второй параллельный проход прибавляет +1 там, где перенос пришёл |
| **Carry-lookahead (scan)** | `vectorized._add_digits` (numpy и CUDA) | каждый разряд: generate / propagate / kill; перенос в k = «ближайший слева не-propagate разряд был generate». Находится через `cumsum` + gather без цикла по разрядам |

### Одно число (base 2⁶⁴, numpy-массивы)

| лимбов | python | numpy | C (adc) | numba | cuda |
|--------|--------|-------|---------|-------|------|
| 10³ | 476 µs | 64 µs | 23 µs | **16 µs** | 1.3 ms |
| 10⁵ | 57 ms | 3.7 ms | 0.60 ms | **0.48 ms** | 2.1 ms |
| 10⁶ (≈19 млн десятичных цифр) | 762 ms | 45 ms | 3.6 ms | **3.4 ms** | 10 ms |
| 10⁷ | — | 473 ms | 85 ms | **79 ms** | 93 ms |

- **Упираемся в память, а не в вычисления.** Одно сложение на 8 байт — слишком мало работы, поэтому 12 ядер numba почти не обгоняют один поток C с `adc`.
- **Carry-lookahead делает ~10 проходов по данным вместо одного.** На CPU это в 6–13 раз медленнее. На GPU вычисления бесплатны, но копирование 3×80 МБ по PCIe съедает выигрыш. Если бы данные уже лежали на GPU, он бы выиграл. Поэтому в `auto` GPU не участвует.
- **Главное ускорение дал не алгоритм, а то, что вокруг горячего цикла.** Проверка цифр (`min`/`max`, два лишних прохода) и `flatnonzero` для срезания нулей стоили больше самого сложения. После их удаления C ускорился с 22 ms до 3.6 ms на 10⁶ лимбов.
- **Маленькие числа:** до ~256 лимбов Python быстрее, потому что вызов через ctypes и конвертация в numpy стоят около 30 µs. Поэтому `UInt256` (4 лимба) остаётся на Python, а у `auto` порог `min_n=256`.
- **У numba `parallel=True` высокая плата за вызов (~1 ms)**, так что для небольших входов нужна отдельная последовательная версия функции. Плюс первый вызов JIT-компилирует функцию (~1 s, дальше кэш на диске).

### Аудит: Σ N балансов uint256 (`algos.sum_limbs`, carry-save)

Вместо N сложений с переносом суммируем **столбцы** лимбов, а переносы разрешаем один раз в конце. Чтобы столбец не переполнился, 64-битный лимб режем на две 32-битные половины. Так устроены аппаратные умножители (дерево carry-save сумматоров).

| N балансов | UInt256 по одному | Python int | python (столбцы) | numpy | cuda | **numba** |
|------------|-------------------|------------|------------------|-------|------|-----------|
| 10³ | 30 ms | 2.4 ms | 0.94 ms | 0.15 ms | 1.1 ms | **0.03 ms** |
| 10⁵ | 3.46 s | 114 ms | 93 ms | 12 ms | 1.9 ms | **0.8 ms** |
| 10⁶ | — | 1.49 s | 1.08 s | 106 ms | 17 ms | **5.4 ms** |
| 10⁷ | — | — | — | 1.29 s | 155 ms | **39 ms** |

- **Алгоритм важнее языка:** переход от сложения по одному к суммированию столбцов даёт ×37 ещё на чистом Python. numba добавляет ещё ×116. Итого на 10⁵ держателей получается **~4300×**.
- **GPU снова упирается в копирование** (320 МБ по PCIe).
- `Ledger.audit()` теперь использует `sum_limbs`. Тест проверяет, что «взломанный» в обход `mint`/`transfer` баланс ловится.

### Как выбирает `auto`
- `add_digits`: numba (от 256) → C (от 256) → numpy (от 1000) → python; cuda только явно.
- `sum_limbs`: numba (от 100) → numpy (от 100) → python; cuda только явно.
- Основания, которые не помещаются в uint64 (2⁶³ < base ≠ 2⁶⁴), автоматически считаются на Python.
