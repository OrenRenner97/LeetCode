# 15. 3Sum

[LeetCode](https://leetcode.com/problems/3sum/) · Medium · Array, Two Pointers, Sorting

## Условие (кратко)
3 ≤ n ≤ 3000, −10⁵ ≤ nums[i] ≤ 10⁵. Вернуть все различные тройки значений `[a, b, c]` из разных позиций с a + b + c = 0.

## Решение (solution.py): перебор всех троек

**Идея:** три вложенных цикла по индексам i < j < k; тройку с нулевой суммой сортируем и кладём в `set` — так одинаковые тройки значений склеиваются.

**Время:** O(n³) · **Память:** O(t), t — число троек в ответе

Корректно: сверено с эталоном на 2 тыс. случайных массивов (узкие и широкие диапазоны, много повторов).

Что можно улучшить:
- **Главное — асимптотика.** На максимуме LeetCode C(3000, 3) ≈ 4.5·10⁹ проверок. n = 300 — 0.95 s, значит n = 3000 — около 16 минут: Time Limit Exceeded. Задача решается за O(n²) — сведением к Two Sum (см. ниже).
- **`sorted([...])` на каждую найденную тройку** — можно один раз отсортировать `nums`: при i < j < k тройка выйдет уже упорядоченной.
- **Возвращается список кортежей**, а сигнатура обещает `list[list[int]]`. Судья LeetCode, скорее всего, сериализует кортежи так же, но контракт нарушен: `result[0].append(...)` упадёт.
- **Нет раннего выхода:** после сортировки при `nums[i] > 0` дальше все три числа положительные, сумма нулём быть не может.

## Шаг 1. Альтернативы (alternatives.py)

Python 3.12, медиана из 3–5 прогонов. Ноутбук шумит ±30%.

| Подход | Время | Память | wide 300 | wide 3000 | narrow 3000 | range 3000 | Идея |
|--------|-------|--------|------|------|------|------|------|
| Solution | O(n³) | O(t) | 0.94 s | ~16 мин | — | — | все тройки индексов + `set` отсортированных кортежей |
| Combinations | O(n³) | O(t) | 1.37 s | — | — | — | то же через `itertools.combinations` по отсортированному |
| **SortTwoPointers** | O(n²) | O(1) | 7.6 ms | 985 ms | 36 ms | 1.38 s | сортировка, фиксируем a, пара — двумя указателями |
| SortHashSet | O(n²) | O(n) | 10 ms | 1.22 s | 43 ms | 2.90 s | сортировка, фиксируем a, пара — как в Two Sum через `set` |
| **CounterValues** | O(n + u²) | O(u) | 6.1 ms | 497 ms | **1.3 ms** | **1.11 s** | `Counter`, пары различных значений a ≤ b, c = −a−b ищем в счётчике |
| SignSplit | O(n²) | O(n) | **4.3 ms** | 598 ms | 1.86 s | 3.43 s | группы по знаку: пары одного знака + число другого |
| NumpySearchsorted | O(n² log n) | O(n) | 7.4 ms | **352 ms** | 97 ms | 3.34 s | для каждого a векторно: все c = −a−b через `searchsorted` |

Входы: wide — случайные из [−10⁵, 10⁵] (как в LeetCode, значения почти все различные, троек мало); narrow — из [−50, 50] (101 различное значение на 3000 чисел); range — все числа от −n/2 до n/2 (≈ 1.1 млн троек на n = 3000).

- **Главный выигрыш — асимптотика, а не реализация.** O(n³) → O(n²) на n = 300 даёт ×100–1000. Остальные варианты между собой расходятся в 2–3 раза, кроме патологий.
- **Как работают два указателя.** Массив отсортирован, a зафиксировано, ищем b + c = −a на отрезке [l, r]. Сумма мала — `nums[l]` не подходит ни с каким c (все c левее r ещё меньше), выбрасываем его: `l += 1`. Велика — симметрично `r -= 1`. Каждый шаг выбрасывает одно число, поэтому O(n) на a. Дубликаты не возникают вовсе: одинаковые a и одинаковые b/c после находки просто пропускаем — `set` не нужен.
- **SortHashSet — то же O(n²), но медленнее в 1.2–2 раза:** на каждый шаг — хэширование и вставка в `set`, плюс дедупликация через `set` троек. Указатели обходятся сравнениями и сложением.
- **CounterValues лучший на повторах.** Ответ зависит только от различных значений и их кратностей: перебор идёт по u², а не n². narrow: u = 101, 1.3 ms против 36 ms у указателей (×28). Без повторов (u ≈ n) — всё равно лидер среди чистого Python: внутренний цикл короткий и рано обрывается на `c < b`.
- **SignSplit — быстрый на «честных» данных и катастрофа на повторах.** Пары перебираются только внутри одной группы знака (≈ n²/4 вместо n²/2), а третье число ищется в `set` — на wide это быстро. Но повторяющиеся значения не схлопываются: narrow 3000 — 1.86 s, ×1500 к CounterValues. Урок: дедупликация на входе (по значениям) дешевле, чем на выходе (через `set` троек).
- **NumpySearchsorted выигрывает, когда троек мало** (wide 3000 — 352 ms, лучший): внутренний цикл по b уходит в C. Но Python-цикл по a остался, на каждый шаг — несколько аллокаций массивов; когда ответ огромный (range), всё съедают `column_stack`, `np.unique` по строкам и `tolist()`.
- **range упирается в размер ответа:** ≈ 1.1 млн троек; создание списков `[a, b, c]` — существенная часть времени у всех.
- **Combinations медленнее ручного перебора:** `itertools` выносит в C только цикл, а на каждую тройку остаётся вызов `sum(t)` и создание кортежа. Внутренняя работа не ушла из Python — перенос цикла в C ничего не дал.
- **Предел.** Для 3Sum O(n²) — практический потолок: заметно субквадратичных алгоритмов неизвестно (гипотеза 3SUM, на ней строится класс 3SUM-hard задач). Обобщение: k-Sum = сортировка + рекурсия до 2Sum на указателях, O(n^(k−1)).

## Шаг 1.5. Библиотека → `algos.k_sum`
`src/algos/hashing/k_sum.py` (рядом с `find_pair_with_sum` из Two Sum: в основе тот же поиск дополнения в словаре). Отличия от LeetCode-версии:
- **Любое `k ≥ 1` и любая `target`:** `k_sum(nums)` — 3Sum, `k_sum(nums, target, k=4)` — 4Sum (задача 18), `k=2` — все различные пары Two Sum, `k=1` — есть ли значение.
- **Детерминированный ответ:** набор — кортеж по возрастанию, список отсортирован лексикографически. Нет наборов или k > n — `[]` (это нормальный ответ, а не ошибка, поэтому не `None`).
- **Только целые:** int, numpy-целые (массив и скаляры через `__index__`), длинная арифметика. float → `TypeError`: `0.1 + 0.2 - 0.3 != 0`, ответ зависел бы от порядка сложения; дробные — переводить в целые (копейки).
- **Валидация:** bool, float, строки → `TypeError`; `k < 1` → `ValueError`. Вход не меняется, принимает любой iterable.

Реализация — CounterValues, обобщённая рекурсией: первое значение фиксируется (с уменьшением его кратности), остаток ищется среди значений не меньше; `k = 2` — Two Sum по различным значениям. Отсечения: `min · k > target` и `max · k < target` на каждом уровне; в Two Sum начало сдвигается бинпоиском к `b ≥ target − max` (меньшие b дают c больше максимума). O(n + u^(k−1)).

Цена API, n = 3000, лучшее из 5:

| | wide | narrow | range |
|-|-|-|-|
| SortTwoPointers | 898 ms | 24 ms | 2.21 s |
| CounterValues | 496 ms | 1.3 ms | 2.08 s |
| `k_sum(nums)` | **441 ms** | 1.5 ms | **0.95 s** |

- **Обобщение до k бесплатно:** рекурсивный вызов — один на каждое первое значение, внутренний цикл тот же.
- **range — вдвое быстрее CounterValues из-за кортежей:** 1.1 млн `prefix + (b, c)` дешевле 1.1 млн списков `[a, b, c]`. Когда ответ огромный, формат ответа — значимая часть стоимости.
- **Бинпоиск начала** даёт ~10% на wide: при широком диапазоне значений половина b заведомо мала.
- 4Sum, n = 300 из ±1000: ~0.4 s на 90 тыс. четвёрок.

Тесты `tests/algos/test_k_sum.py`: примеры 3Sum и 4Sum; k = 1, 2; кратности (`[5, 5]` против `[5, 5, 5]`); все target на одном наборе; 3 тыс. случайных против перебора `combinations` при k = 1…5; против `Solution` и `SortTwoPointers` (вплоть до n = 3000); длинные целые; numpy, генератор, неизменность входа; ошибки.
