# 14. Longest Common Prefix

[LeetCode](https://leetcode.com/problems/longest-common-prefix/) · Easy · String, Trie

## Условие (кратко)
1 ≤ n ≤ 200 строк длины ≤ 200 из строчных латинских букв. Вернуть самый длинный общий префикс всех строк или "".

## Решение (solution.py): горизонтальный проход

**Идея:** префикс = первая строка. Для каждой строки обрезаем его до длины строки, затем посимвольно ищем первое расхождение и обрезаем до него.

**Время:** O(S), S — суммарная длина строк · **Память:** O(m) на срезы

Корректно: сверено с эталоном на 3 тыс. случайных наборов (пустые строки, одна строка, строки-префиксы друг друга) и на входах максимального размера.

Что можно улучшить:
- **Нет раннего выхода.** Префикс стал "" — ответ уже известен, а цикл идёт по всем остальным строкам (с `min`, `len`, срезом на каждой). На firstdiff (вторая строка расходится в первом символе) при n = 10⁴ — 8 ms вместо 1 µs.
- **Строка, которая уже начинается с префикса, всё равно проверяется посимвольно.** Это основной случай (у ответа длины m каждая строка его содержит), и он стоит m итераций Python-цикла на строку. `word.startswith(prefix)` проверяет то же на C. На same (все строки одинаковые, 200 × 200) — 4.1 ms против 36 µs, ×110.
- **`min(len(...), len(word))` считается дважды:** после первого среза `len(result_common_prefix) ≤ len(word)`, второй `min` всегда равен длине префикса.
- **Первая итерация сравнивает `strs[0]` с самой собой** — 200 лишних сравнений. `for word in strs[1:]` или `islice(strs, 1, None)`.
- Имя `result_common_prefix` длинное для переменной, которая живёт 8 строк; `prefix` читается не хуже.

## Шаг 1. Альтернативы (alternatives.py)

Строки длины 200, Python 3.12, медиана из 7. Ноутбук шумит ±30%.

| Подход | Время | Память | same 200 | same 10⁴ | half 10⁴ | lastdiff 10⁴ | firstdiff 10⁴ | Идея |
|--------|-------|--------|------|------|------|------|------|------|
| Solution | O(S) | O(m) | 4.1 ms | 162 ms | 103 ms | 201 ms | 8.0 ms | горизонтально, посимвольно в Python, без раннего выхода |
| HorizontalEarlyExit | O(S) | O(m) | **36 µs** | 1.3 ms | 2.0 ms | 1.7 ms | **1.1 µs** | `startswith` на C + выход на пустом префиксе |
| VerticalZip | O(n · m) | O(n) | 1.1 ms | 94 ms | 57 ms | 1.0 ms | 1.2 ms | по столбцам `zip(*strs)` + `set` |
| **MinMax** | O(S) | O(1) | 40 µs | **1.0 ms** | **1.2 ms** | **0.6 ms** | 0.7 ms | префикс лексикографических min и max |
| StartswithShrink | O(n · m²) | O(m) | 39 µs | 2.3 ms | 2.3 ms | 1.5 ms | 40 µs | отрезаем по символу, пока не `startswith` |
| BinarySearchLength | O(S · log m) | O(m) | 323 µs | 21 ms | 3.0 ms | 14 ms | 0.4 ms | бинпоиск по длине, проверка `all(startswith)` |
| NumpyMatrix | O(n · L) | O(n · L) | 82 µs | 9.2 ms | 9.3 ms | 8.3 ms | 6.5 ms | матрица байт n × L, первый «плохой» столбец |

Входы: same — все строки одинаковые (префикс = 200); half — общие 100 символов + случайный хвост; lastdiff — одинаковые, кроме последней (расходится в 1-м символе, ответ ""); firstdiff — вторая строка расходится в 1-м символе. Полный вывод с n = 200 — в скрипте.

- **Вся разница — сколько работы уходит в C.** Все варианты линейны (кроме бинпоиска), а разброс ×100–300. Solution на каждый символ делает итерацию Python-цикла; HorizontalEarlyExit и MinMax сравнивают строки целиком (`startswith`, `<` в `min`/`max` — это `memcmp`).
- **MinMax — лучший универсальный.** `min` и `max` по n строкам — 2n сравнений строк на C, обычно на первых символах; дальше один Python-цикл по префиксу двух строк. Не зависит от того, *где* расходятся строки. Так устроен `os.path.commonprefix`. Минус — всегда смотрит все строки: на firstdiff в 600 раз медленнее раннего выхода.
- **HorizontalEarlyExit побеждает, когда расхождение рано.** firstdiff — 1 µs: вторая строка, префикс пуст, выход. На same почти догоняет MinMax: `startswith` 10⁴ раз по 200 байт.
- **VerticalZip хорош только при раннем расхождении в столбце:** `zip(*strs)` строит кортеж из n символов на столбец + `set` — дорого при длинном ответе (94 ms на same), зато на lastdiff выходит на первом столбце.
- **StartswithShrink** — короче всех по коду. Квадратичность по длине на практике не видна: обрезание идёт только до первого `startswith`, и `startswith` на C.
- **BinarySearchLength — тот случай, когда асимптотика не помогает:** log m проходов по всем строкам вместо одного. Имеет смысл, когда проверка «все начинаются с p» дешёвая и внешняя (например, запрос к индексу), а не здесь.
- **NumpyMatrix проигрывает из-за конвертации:** `np.array(strs, dtype=bytes)` — это кодирование и копирование всех n · L байт; само сравнение быстрое. Если данные уже лежат матрицей байт (fixed-width поля из файла), картина другая.

## Шаг 1.5. Библиотека → `algos.common_prefix`
`src/algos/strings/prefix.py` (новая техника `strings/`). Отличия от LeetCode-версии:
- **Любые последовательности одного типа:** `str`, `bytes`, `list`, `tuple`; тип результата = тип элементов. Элементы списков сравниваются только через `==` — подойдут и несравнимые (dict, смесь типов).
- **Пустой набор → `None`**; пустой префикс — это `""` / `b""` / `[]` / `()`, а не `None`. Принимает любой iterable, генератор тоже.
- **`sep` — префикс только из целых компонент.** `os.path.commonprefix(["/usr/lib", "/usr/local"])` даёт `"/usr/l"`, а `common_prefix(..., sep="/")` — `"/usr/"`. Компонента целая, если у каждого элемента за префиксом конец или `sep`: `["/usr/lib", "/usr/lib/x"]` → `"/usr/lib"`. Многосимвольный `sep` (`"::"`) тоже работает. Для путей, S3-ключей, имён метрик `a.b.c`.
- **Валидация:** не str/bytes/list/tuple или разные типы → `TypeError`; `sep` не того типа → `TypeError`, пустой → `ValueError`.

Реализация:
- **str/bytes — MinMax**, но расхождение min и max ищется не посимвольно, а бинпоиском по длине через `startswith`: log m шагов Python вместо m. Плюс быстрый путь: `max.startswith(min)` — все строки начинаются с min (в т.ч. все равны), ответ сразу.
- **list/tuple — HorizontalEarlyExit**: порядка на элементах может не быть, поэтому только `==`, с выходом на пустом префиксе.

Цена API, 200 строк длины 200, лучшее из 7:

| | same | half |
|-|-|-|
| Solution | 2.3 ms | 1.2 ms |
| MinMax (без проверок) | 19 µs | 15 µs |
| `os.path.commonprefix` | 24 µs | 22 µs |
| `common_prefix(strs)` | **14 µs** | 19 µs |
| `common_prefix(strs, sep=...)` | 28 µs | 24 µs |

- **Проверка типов генератором стоила ~30% вызова.** `any(type(s) is not kind for s in seqs)` — это Python-цикл по всем строкам; `set(map(type, seqs))` — тот же проход на C. Тот же урок, что в задаче 11: валидация на n элементах должна идти на C.
- **Бинпоиск по длине окупается на длинном общем префиксе** (same — быстрее MinMax), на half примерно вровень.
- `sep` добавляет ещё один проход `startswith` по всем строкам — ×1.5–2.

Тесты `tests/algos/test_common_prefix.py`: LeetCode-примеры; 5 тыс. случайных наборов против `Solution` и эталона во всех четырёх типах; строки по 10⁵ символов; пустые и вырожденные случаи; несравнимые элементы списков; `sep` — пути, точки, многосимвольный, bytes, элемент списка + 5 тыс. случайных против эталона; ошибки.
