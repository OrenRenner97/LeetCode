# 7. Reverse Integer

[LeetCode](https://leetcode.com/problems/reverse-integer/) · Medium · Math

## Условие (кратко)
Дано 32-битное знаковое `x` (−2³¹ ≤ x ≤ 2³¹ − 1). Вернуть его цифры в обратном порядке (знак сохраняется, ведущие нули пропадают: 120 → 21). Если результат не помещается в [−2³¹, 2³¹ − 1], вернуть 0. Среда считается неспособной хранить 64-битные числа: промежуточные значения тоже должны помещаться в 32 бита.

## Решение (solution.py): разворот строки + `bit_length`

**Идея:** `int(str(abs(x))[::-1])` даёт модуль разворота. Дальше он проверяется по числу битов: у положительных допустимо ≤ 31 бит (это ровно `r ≤ 2³¹ − 1`), у отрицательных — < 32 бит.

**Время:** O(d), d ≤ 10 цифр · **Память:** O(d)

Корректно на всех входах: сверено с эталоном на 40 тыс. случайных x и на ~8.6 тыс. x, чей разворот лежит в ±5000 от границ.

Что можно улучшить:
- **Условие про 32 бита не выполнено.** Сначала строится большое число (до 9 646 324 351, 34 бита), потом проверяется. В Python это работает, потому что int неограничен; в C/Java на этом месте уже произошло бы переполнение. Как сделать честно — PopPushGuard, NegativeAccumulate, Wraparound32 ниже.
- **Граница для отрицательных верна «случайно».** `bit_length() >= 32` значит `r ≥ 2³¹`, а допустим и сам `r = 2³¹` (ответ −2³¹). Но такого разворота не бывает: для него нужен x = −8 463 847 412, вне диапазона. Яснее сравнивать сам результат с `[INT_MIN, INT_MAX]` (StrCompare): тогда не нужно это доказывать.
- **Проверки `x.bit_length()` мёртвые.** У положительного x не бывает больше 31 бита; 32 бита только у x = −2³¹, а его разворот 8 463 847 412 (33 бита) и так отсекается проверкой `reversed_x`.
- **`bit_length` — сравнение со степенью двойки, а граница — не степень.** Здесь совпало (2³¹ − 1 — ровно все 31-битные числа), но первая версия с `31 - 1 / 2**31` сломалась именно на этом: `bit_length` целый, дробная граница превратила `> 31` в `>= 31` и отбросила все ответы от 2³⁰ до 2³¹ − 1. Сравнение со значением вместо битов такой ловушки не имеет.

## Шаг 1. Альтернативы (alternatives.py)

| Подход | 32 бита? | Время на 10⁵ вызовов (random) | Идея |
|--------|----------|------------------|------|
| **Solution** | нет | 161 ms | строка, int, `bit_length` |
| StrCompare | нет | 162 ms | строка, int, одно сравнение со знаком |
| **StrLexCompare** | да | **131 ms** | 10-значный разворот сравниваем **как строку** с `"2147483647"`, int только когда влезает |
| PopPushGuard | да | 637 ms | `rev = rev·10 + d`, проверка до шага: `rev > MAX // 10` или `== и d > 7` |
| NegativeAccumulate | да | 964 ms | как в C: копим в отрицательных, потому что −2³¹ есть, а +2³¹ нет |
| Wraparound32 | да | 2 190 ms | как в Java: считаем с обёрткой mod 2³², ловим по `(new − d) / 10 != rev` |

Все O(d) с d ≤ 10: асимптотика одинакова, разница в константе CPython и в том, соблюдено ли условие.

- **StrLexCompare** — неожиданный победитель и при этом честный. Переполнение возможно только у 10-значного разворота, а строки цифр одной длины сравниваются лексикографически так же, как числа. Большой int не появляется никогда, а на переполнении не вызывается даже `int()`. Тот же аргумент, что у Solution: граница для отрицательных та же 2147483647, потому что разворот 2147483648 недостижим (написано в коде).
- **PopPushGuard** — каноничный ответ для собеседования. Проверка *до* умножения: `rev > INT_MAX // 10` — точно не влезет; `rev == INT_MAX // 10` — влезет, только если цифра ≤ 7 (у отрицательных ≤ 8). В Python приходится брать модуль: `//` и `%` округляют к −∞ (`-7 % 10 == 3`), цифры отрицательного числа «не те». Но `abs(−2³¹) = 2³¹` в int32 не существует — в C это UB.
- **NegativeAccumulate** закрывает эту дыру: отрицательных int32 на одно больше, поэтому разворот копится со знаком минус, а знак меняется только в конце (и только если это не −2³¹). Это строгий вариант: ни одно значение не выходит за int32. Деление с усечением к нулю (как `/` и `%` в C) эмулирует `_cdivmod`.
- **Wraparound32** — Java-подход «сначала переполнись, потом проверь»: если шаг обратим, `(new − d) / 10 == rev`, старшие биты не потерялись. В Java переполнение int определено (обёртка), в C для знаковых — UB, поэтому в C так писать нельзя. В Python обёртку приходится эмулировать маской — отсюда ×17.

### Бенчмарк (`uv run benchmarks/reverse_integer.py`)

Пачка из 10⁵ вызовов `[f(x) for x in xs]`, Python 3.12, медиана из 5:

| Вход | StrLexCompare | Solution | StrCompare | PopPushGuard | NegativeAccumulate | Wraparound32 |
|------|---|---|---|---|---|---|
| random (почти все 10-значные, ~половина переполняется) | **131 ms** | 161 ms | 162 ms | 637 ms | 964 ms | 2.19 s |
| small (\|x\| < 1000) | **116 ms** | 131 ms | 129 ms | 254 ms | 375 ms | 615 ms |
| overflow (только переполнения) | **88 ms** | 132 ms | 145 ms | 662 ms | 979 ms | 2.29 s |

Выводы:
- **Строковые варианты в 2–26 раз быстрее арифметики.** `str`, срез `[::-1]` и `int` — это C-циклы по цифрам внутри одной операции, а `divmod` в Python-цикле — десять итераций байткода. Из 1.3 µs на вызов Solution ~0.1 µs — сам вызов метода, ~0.6 µs — `str(abs(x))[::-1]`, ~0.3 µs — `int(...)`.
- **На «overflow» StrLexCompare выигрывает больше всего (×1.5):** там он вообще не вызывает `int()`.
- **Ранний выход у арифметики не помогает.** Переполнение обнаруживается только на последней, 10-й цифре, поэтому на «overflow» PopPushGuard не быстрее, чем на «random».
- **В C всё наоборот:** арифметика — несколько тактов на цифру без аллокаций, а строка — `sprintf` и разбор. Поэтому «правильный» ответ зависит от языка: в Python — строки, в C/Java — PopPushGuard / NegativeAccumulate.

## Шаг 1.5. Библиотека → `algos.reverse_digits`
`src/algos/arithmetic/reverse.py` (рядом с `to_digits`/`from_digits` из задачи 2). LeetCode 7 = `reverse_digits(x, bits=32) or 0`. Отличия от LeetCode-версии:
- **`None` вместо 0 при переполнении.** У LeetCode 0 — и «не влезло», и законный ответ `reverse(0)`, их не различить.
- **`width` — разворот в фиксированной ширине**: 120 при `width=4` → «0120» → «0210» = 210. Без ширины разворот не обратим (12, 120 и 1200 дают 21), с шириной — взаимно однозначен. Именно это понадобилось в бизнесе.
- **Любые `base` (2…36), `bits`, `signed`**: int8, uint64, двоичный разворот битов (`base=2, width=8`).
- **Валидация**: `bool` не int; вход, который сам не влезает в `bits` бит, — `ValueError` (это ошибка вызова, а не «переполнение результата»).
- Реализация — строка для основания 10 (по замерам шага 1 в 2–5 раз быстрее `divmod`), `divmod` для остальных оснований и для чисел длиннее ~3 600 цифр: `str()`/`int()` в CPython 3.12 отказываются работать с числами больше 4 300 цифр (тест это ловит).
- Проверяется результат, а не промежуточные значения: в Python 32-битная дисциплина ничего не даёт (обоснование — шаг 1).
- Рядом `int_range(bits, signed)` и `is_digit_palindrome(x, base)` — задел на LeetCode 9.

Тесты `tests/algos/test_reverse_digits.py`: эквивалентность с PopPushGuard на 20 тыс. случайных int32, биекция при `width` 1–4 (все значения), основания 2–36 против эталона на списке цифр, огромные числа, валидация.

## Шаг 2. Бизнес-кейс → `biz.infra.rowkeys`
**Боль.** В HBase, Bigtable и других хранилищах, где таблица режется на регионы по диапазонам ключа, последовательные id (номера заказов, автоинкремент) пишутся в один регион — hotspot. Стандартный приём — «развернуть ключ»: младшая, самая быстро меняющаяся цифра id становится первой.

**Связь с задачей.** Разворот — это LeetCode 7, и оба его подвоха становятся инцидентами:
- **ведущие нули**: без фиксированной ширины 12, 120 и 1200 дают один ключ 21 и перезаписывают друг друга → `width`;
- **переполнение**: ключ шириной 19 цифр в int64-колонке не влезает у **7.8%** id подряд (id на …99 → 9.9·10¹⁸ > 2⁶³ − 1) → `max_safe_width`, `audit`, `KeyOverflow`.

Результат: 100 000 заказов подряд на 16 регионов — прямой ключ 100% в одном регионе, развёрнутый 6.25% в каждом (skew 16 → 1.00). Цена — диапазонный запрос по id обходит все регионы; это в README модуля.

Подробности: `src/biz/infra/rowkeys/README.md`. API: `POST /v1/infra/rowkeys/encode`, `/decode`, `/hotspot`.
