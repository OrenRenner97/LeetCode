# 3. Longest Substring Without Repeating Characters

[LeetCode](https://leetcode.com/problems/longest-substring-without-repeating-characters/) · Medium · Hash Table, String, Sliding Window

## Условие (кратко)
Длина самой длинной **подстроки** (непрерывного куска) без повторяющихся символов.

Обозначения: n — длина строки, σ — размер алфавита (по условию ~95 печатных ASCII), L — ответ (L ≤ σ).

## Решение (solution.py): «нерастущее окно наоборот»

**Идея:** окно **никогда не сжимается**. Его длина всегда равна «лучший ответ + 1»:
- окно без повторов → нашли ответ длиннее, окно растёт (двигается только правый край);
- в окне повтор → окно **сдвигается целиком** (оба края на 1), длина та же.

Это известный приём для задач «самое длинное окно со свойством», которое сохраняется у подокон.

**Почему это верно.** Правый край проходит каждую позицию r. Если существует подстрока без повторов длиной ≥ best+1, заканчивающаяся в r, то её суффикс длиной ровно best+1 тоже без повторов, и именно он будет проверен на шаге r. Значит, ответ не пропускается.

**Время:** O(n·L): на каждом шаге срез `s[left:right+1]` и `set` от него стоят O(L). При L ≤ 95 это «O(n) с константой до 95», поэтому LeetCode с n ≤ 5·10⁴ проходит.
**Память:** O(L) на временные срез и set.

Что можно улучшить:
- **Проверка за O(1) вместо O(L).** Хранить счётчики символов окна и число символов с `count > 1`. Тогда «есть ли повтор» — это `dups > 0`, без среза и set. Идея та же, но O(n) — см. `NonShrinkingCounts`, в 8–13 раз быстрее.
- Ответ можно не хранить отдельно: в конце он равен длине окна, `len(s) - left`.
- `max(max_length, len(substring))` в ветке «без повторов» всегда даёт `len(substring)`, потому что окно на 1 длиннее лучшего.

## Шаг 1. Альтернативы (alternatives.py)

| Подход | Время | Память | Комментарий |
|--------|-------|--------|-------------|
| Solution (твой) | O(n·L) | O(L) | окно не сжимается; срез + set на каждом шаге |
| BruteForce | O(n·L) | O(L) | от каждого начала растим set до первого повтора |
| WindowSet | O(n) | O(L) | классика: левый край ползёт по одному, пока повтор не уйдёт |
| NonShrinkingCounts | O(n) | O(σ) | **твоя идея за O(n)**: счётчики + число дублей |
| **LastIndex** | **O(n)** | O(σ) | dict «символ → последняя позиция»; левый край **прыгает** |
| **LastIndexArray** | **O(n)** | O(256) | то же, но список на 256 ячеек вместо dict |

### Ключевая идея оптимума: прыжок вместо ползания
WindowSet при повторе удаляет символы слева **по одному**. LastIndex помнит, где символ был в последний раз, и сразу ставит левый край за ним:

```python
prev = last.get(ch, -1)
if prev >= left:        # прошлое вхождение ВНУТРИ окна
    left = prev + 1
```

**Ловушка `abba`:** на второй `a` прошлое вхождение (0) уже **левее** окна (left = 2). Без проверки `prev >= left` (или `left = max(left, prev+1)`) левый край уехал бы **назад**. Этот случай есть в тестах.

### Почему не O(n²)
Подстрока без повторов не может быть длиннее алфавита, поэтому даже перебор стоит O(n·σ), а не O(n²). При σ = 95 это заметная, но константа. Для Unicode-текста (σ до 1.1 млн) перебор и твой вариант деградировали бы до O(n²), а LastIndex остаётся O(n).

### Бенчмарк (`uv run benchmarks/longest_substring.py`)

| вход, n = 10⁶ | Solution | BruteForce | WindowSet | NonShrinkingCounts | LastIndex | LastIndexArray |
|---------------|----------|------------|-----------|--------------------|-----------|----------------|
| ДНК `acgt` (L ≈ 4) | 0.95 s | 1.31 s | 0.81 s | 0.42 s | 0.23 s | **0.19 s** |
| случайные 95 символов (L ≈ 15–20) | 3.29 s | 3.14 s | 0.65 s | 0.39 s | 0.20 s | **0.14 s** |
| 95 символов по кругу (L = 95) | 5.09 s | 21.9 s | 0.49 s | 0.38 s | 0.45 s | **0.17 s** |

- **Твоё решение замедляется вместе с L**: при L = 4 оно в 5 раз медленнее лучшего, при L = 95 уже в 30 раз. Это и есть O(n·L) на практике.
- **`NonShrinkingCounts` (твоя идея без среза) стабильно 0.4 s** на любом входе: O(n) честно.
- **Список вместо dict даёт ×1.2–2.6.** На входе «по кругу» у dict много перезаписей ключей, а у списка это просто запись по индексу.
- На n = 5·10⁴ (лимит LeetCode) все варианты укладываются в доли секунды, поэтому твоё решение и проходит.

## Шаг 1.5. Библиотека → `algos.longest_unique_window`

`src/algos/sliding_window/unique_window.py`:

```python
longest_unique_window(seq, *, max_repeats=1, backend=None) -> tuple[int, int]   # [start, end)
```

Отличия от LeetCode-версии:
- **позиция, а не только длина**: `(start, end)`, длина = `end - start`. Бизнесу почти всегда нужно «где», а не «сколько»;
- **любая последовательность**, а не только строка: список id, кортежи событий — всё, что хэшируется;
- **`max_repeats=k`**: каждый элемент встречается не больше k раз. При k = 1 это исходная задача;
- **детерминированный ответ**: из нескольких самых длинных окон возвращается самое левое (обновление только при строго большей длине).

Как устроено внутри:
- k = 1 → **LastIndex**: левый край прыгает за прошлое вхождение;
- k > 1 → **счётчики**: прыгнуть нельзя (непонятно, какое из k вхождений выкинуть), поэтому левый край ползёт. Каждый элемент входит и выходит по разу, так что всё равно O(n).

## Шаг 2. Бизнес-кейс: антифрод, card testing → `biz.fintech.antifraud`

**Боль.** Мошенник с базой украденных карт с одного IP или устройства делает подряд много мелких платежей, каждый раз с **новой** картой, чтобы найти живые. Большинство отклоняется. Обычный покупатель пользуется одной-двумя картами.

**Связь с задачей.** «Строка» — отпечатки карт в попытках одного источника по времени. «Подстрока без повторов» — разные карты подряд. Длинное окно плюс много отказов означают перебор.

| Правило | Смысл |
|---------|-------|
| `min_cards=5` | столько разных карт подряд — уже тревога |
| `max_repeats=1` | строго разные карты; `2` ловит обход «каждую карту по два раза» |
| `high_decline_rate=0.5` | отказов ≥ 50% → `HIGH` → `block`, иначе `MEDIUM` → `review` |

Что даёт обобщение из шага 1.5:
- **позиция окна** превращается в конкретные попытки для расследования (`attempt_ids`) и в длительность атаки;
- **`max_repeats`** закрывает простой обход детектора повторами;
- **любой тип элементов** позволяет передавать отпечатки карт (хэши), а не символы.

Бизнес-детали: номер карты (PAN) детектору не передаётся, только отпечаток (PCI DSS), и API отклоняет то, что похоже на номер карты. Детектор сам группирует поток по источникам и сортирует по времени. Офис за общим IP с 5 картами без отказов получает `review`, а не блокировку.

```bash
uv run python -m biz.fintech.antifraud.demo     # грубый мошенник → block; «хитрый» ловится только с max_repeats=2; офис → review
```

Подробности: [`src/biz/fintech/antifraud/README.md`](../../src/biz/fintech/antifraud/README.md). API: `POST /v1/fintech/antifraud/card-testing`.

## Шаг 3. Скорость

`uv run benchmarks/longest_substring_backends.py`. Железо: i5-13420H (12 потоков), RTX 3050 Laptop. Разброс ±30%.

### Реализации

| backend | Как | Где |
|---------|-----|-----|
| numba / C | LastIndex на **массиве** вместо dict: id сжаты в `[0, m)`, `last[id]` — просто индекс | `numba_impl._luw_core`, `native/c/unique_window.c` |
| numpy / cuda | **без цикла**: `left[i] = cummax(prev_k[i] + 1)`, см. ниже | `vectorized.unique_window_numpy` |
| batch numba | `prange` по источникам, один буфер на поток, после источника обнуляются только тронутые ячейки | `numba_impl._luw_batch_par` |
| batch numpy / cuda | ключ `(источник << 32) \| id` + тот же накопленный максимум через все источники | `vectorized.unique_window_batch_numpy` |

**Формула без цикла.** Пусть `prev_k[i]` — позиция k-го предыдущего вхождения того же значения (её находит стабильная сортировка). Окно, заканчивающееся в i, не может начаться раньше `prev_k[j] + 1` ни для какого j ≤ i, поэтому:

```
left[i] = max(prev_k[0] + 1, …, prev_k[i] + 1)      # накопленный максимум (scan)
```

В CuPy нет `maximum.accumulate`, поэтому там удвоение шага (Hillis–Steele): `x[d:] = max(x[d:], x[:-d])` для d = 1, 2, 4, …, всего log₂(n) параллельных проходов. В пакетной версии максимум «протекает» через границы источников, но значения из прошлых источников всегда меньше начала текущего, так что `max(начало_источника, …)` всё исправляет.

### Одна последовательность (numpy-массив)

| n | python (list) | numpy | cuda | C | numba |
|---|---------------|-------|------|---|-------|
| 10³, 95 символов | — | 118 µs | 1.2 ms | 19 µs | **19 µs** |
| 10⁶, 95 символов | 174 ms | 233 ms | 19 ms | 13 ms | **7.7 ms** |
| 10⁷, 95 символов | — | 3.3 s | 224 ms | **75 ms** | 183 ms |
| 10⁶, id карт до 2⁴⁰ | 670 ms | 101 ms | 98 ms | 84 ms | **85 ms** |
| 10⁷, id карт до 2⁴⁰ | — | 2.2 s | **1.26 s** | 1.31 s | 1.38 s |

- **Массив вместо словаря даёт ×20**: `last[id]` — просто запись в память, без хэширования.
- **На разреженных id главное — сжать их.** Сначала было `np.unique` (сортировка, O(n log n)): 3.1 s на 10⁷, и все бэкенды упирались в неё. Замена на **хэш-таблицу на numba** (та же открытая адресация, что в Two Sum) дала 1.3 s. Задача 1 помогла задаче 3.
- **Векторный scan проигрывает даже Python** (O(n log n) и около 10 проходов по памяти), поэтому в `auto` его нет. GPU окупается только на 10⁷ с разреженными id.

### Детектор целиком: закон Амдала

| этап `scan()` на 10⁶ попыток | время |
|------------------------------|-------|
| группировка Python-объектов по источнику | 1.11 s |
| сортировка внутри источников | 0.46 s |
| плоский список + словарное кодирование отпечатков | 0.28 s |
| **сам алгоритм**: python / numba | 0.275 s / **0.065 s** |
| итого `scan`: python / numba | 2.4 s / 2.1 s |

- **Алгоритм ускорился в 4 раза, а весь `scan` — всего на 15%**: алгоритм занимал около 12% времени, остальное — работа с Python-объектами. Ускорить можно только ту часть, которую ускоряешь.
- **Ловушка:** первая версия пакетного пути была **медленнее** Python (2.6 s против 2.0 s). Миллион строк-отпечатков уходил в `np.unique`, сортировка строк съедала весь выигрыш. Лечение — словарное кодирование в бизнес-слое (`ids.setdefault(fp, len(ids))`).
- **Следующий шаг — колоночные данные с самого начала** (Kafka/Parquet → numpy-массивы `source_id`, `ts`, `card_id`) без объектов `PaymentAttempt`. Тогда весь `scan` займёт десятки миллисекунд.
- **Потоковый детектор** (`StreamingCardTestingDetector`): **430 000 попыток/с** на чистом Python, каждая проверяется за O(1) амортизированно. Для онлайна это правильная архитектура, а пакетный режим нужен для ночных отчётов.

### Как выбирает `auto`
- `longest_unique_window`: для numpy-массивов numba → C; для списков и строк всегда python (конвертация дороже работы). numpy и cuda только явно.
- `longest_unique_window_batch`: numba → python; numpy и cuda только явно.
