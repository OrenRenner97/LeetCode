# 9. Palindrome Number

[LeetCode](https://leetcode.com/problems/palindrome-number/) · Easy · Math

## Условие (кратко)
Дано целое `x` (−2³¹ ≤ x ≤ 2³¹ − 1). Вернуть `True`, если оно читается одинаково слева направо и справа налево. Отрицательные — никогда (`"-121"` справа налево — `"121-"`), с нулём на конце — никогда, кроме самого 0. Follow-up: без перевода в строку.

## Решение (solution.py): сравнение строки с её разворотом

**Идея:** `str(x) == str(x)[::-1]`. Отрицательные отсекаются сами: минус есть только слева.

**Время:** O(d), d ≤ 10 цифр · **Память:** O(d)

Корректно на всех входах: сверено с эталоном на всех x из [−100, 10⁵] и на 30 тыс. случайных x, палиндромов и «почти палиндромов».

Что можно улучшить:
- **`str(x)` вычисляется дважды.** Сохранить в переменную — это `StrOnce`, на 15–20% быстрее.
- **Отрицательные проходят полный путь.** `x < 0` → `False` без строки: на случайном входе половина чисел отрицательная, отсюда основной выигрыш StrOnce (×1.7 на «random»).
- **Follow-up не выполнен.** Для Python это правильный выбор (ниже замеры: строка в 2–7 раз быстрее арифметики), но на собеседовании ждут `HalfReverse`.

## Шаг 1. Альтернативы (alternatives.py)

| Подход | Строка? | random | positive | palindrome | Идея |
|--------|---------|--------|----------|------------|------|
| Solution | да | 74 ms | 76 ms | 60 ms | `str(x) == str(x)[::-1]` |
| **StrOnce** | да | **43 ms** | **63 ms** | **59 ms** | строка один раз, `x < 0` сразу `False` |
| StrHalf | да | 66 ms | 105 ms | 110 ms | сравнение только половин `s[:h] == s[:-h-1:-1]` |
| FullReverse | нет | 174 ms | 335 ms | 322 ms | развернуть всё число через `divmod` и сравнить |
| **HalfReverse** | нет | 105 ms | 184 ms | 182 ms | разворачивать младшую половину, пока `rev < x` (официальный ответ) |
| PeelEnds | нет | 126 ms | 242 ms | 412 ms | срезать старшую и младшую цифры, `div = 10^(d−1)` |
| DigitsTwoPointers | нет | 155 ms | 280 ms | 368 ms | цифры в список, два указателя |

10⁵ вызовов `[f(x) for x in xs]`, Python 3.12, медиана из 5. random — равномерно по int32 (половина отрицательных), positive — по [0, 2³¹ − 1] (почти все 10-значные непалиндромы), palindrome — только 10-значные палиндромы (худший случай: ранних выходов нет).

- **HalfReverse** — каноничный ответ без строк. Две тонкости: (1) число с нулём на конце надо отсечь заранее, иначе `10` даёт `x = 0, rev = 1` и `x == rev // 10` → `True`; (2) при нечётной длине средняя цифра оказывается в `rev`, поэтому сравнение `x == rev // 10`. Переполнения нет: `rev` не обгоняет `x`.
- **FullReverse** в Python корректен, но в C/Java разворот `2147483647` = 7 463 847 412 переполняет int32. Переполнившийся разворот палиндромом быть не может, но в C знаковое переполнение — UB, и сравнению доверять нельзя. HalfReverse этой проблемы не имеет и вдвое короче по итерациям.
- **PeelEnds** — красивая идея с ранним выходом на первом несовпадении, но **ранний выход не окупился**: чтобы найти `div = 10^(d−1)`, нужно сначала пройти все d цифр. На непалиндромах он медленнее HalfReverse, на палиндромах — самый медленный (две операции деления на шаг вместо одной).
- **StrHalf медленнее полной строки.** Два среза вместо одного сравнения: на d ≤ 10 копирование ничего не стоит, а лишняя операция байткода — стоит. Экономия половины работы окупилась бы только на очень длинных числах.
- **Строковые варианты в 2–7 раз быстрее арифметики** — тот же вывод, что в задаче 7: `str` и `[::-1]` — C-циклы, `divmod` в Python-цикле — до 10 итераций байткода. В C картина обратная: HalfReverse — несколько тактов, без аллокаций.

### Бенчмарк (`uv run benchmarks/palindrome_number.py`)

Цифры — в таблице выше. Главное: на «random» у всех, кто проверяет `x < 0` первым, время почти вдвое ниже, чем на «positive» — половина входа отсекается одним сравнением. Solution этого не делает, поэтому у него random ≈ positive.

## Шаг 1.5. Библиотека → `algos.arithmetic.is_digit_palindrome`
`src/algos/arithmetic/palindrome.py` (раньше `is_digit_palindrome` лежал в `reverse.py` как задел из задачи 7; переехал в свой модуль). LeetCode 9 = `is_digit_palindrome(x)`. Отличия от LeetCode-версии:
- **Любое основание 2…36**: `is_digit_palindrome(0b1001, base=2)`.
- **`width` — палиндром в фиксированной ширине**: `110` при `width=4` → «0110» — палиндром. Без ширины число с нулём на конце не бывает палиндромом; с шириной ведущие нули значимы (битовые маски, коды фиксированной длины). Семантика та же, что у `reverse_digits(width=...)`.
- **`next_digit_palindrome(x)` / `prev_digit_palindrome(x)`** — ближайший палиндром сверху / снизу за O(d): отразить левую половину на правую, а если вышло не с той стороны от `x` — сдвинуть левую половину на ±1 и отразить снова. Перебор тут не годится: между соседними 10-значными палиндромами до 10⁵ чисел. Переход длины: `prev(1000) = 999`; у `next` переноса в новый разряд не бывает (если левая половина — одни девятки, её отражение уже ≥ x). Задел на LeetCode 564 (Find the Closest Palindrome).
- `prev_digit_palindrome(x < 0)` → `None`: неотрицательных палиндромов ≤ x нет. `next_digit_palindrome(x ≤ 0)` → 0.
- **Валидация**: `bool` не int, `base` вне 2…36 и `width` короче числа — ошибки, в том числе для отрицательного `x` (иначе ошибка вызова пряталась бы за ответом `False`).
- Реализация — строка для основания 10 (быстрый путь без `reverse_digits`), `divmod` для остальных оснований и для чисел длиннее ~3 600 цифр (лимит `str()`/`int()` в CPython 3.12, тест это ловит).

Цена API: `is_digit_palindrome` — 1.1 µs/вызов против 0.43 µs у inline-StrOnce (×2.5: проверки типов и параметров). `next_digit_palindrome` — ~16 µs на 10-значном числе: цифры гоняются через список; для основания 10 можно переписать на срезах строк, если понадобится.

Тесты `tests/algos/test_digit_palindrome.py`: эталон на строковом представлении для оснований 2–36, все `width` 1–5, `next`/`prev` против перебора на [−20, 4000) в четырёх основаниях, случайные 18-значные (соседи возвращают друг друга), числа на 10 000 цифр, валидация.
